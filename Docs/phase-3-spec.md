Module API changes are additive only.

## How to resume from this file alone

1. Read the two tables below: the first row whose status is not `CLOSED` is where to continue; an `IN PROGRESS` row names the repository, commit and run in its Evidence cell.
2. Part A closes before Part B (Part B work that does not depend on Part A may run alongside, but Part A's exit is the first thing to prove). A module's CI must be green before the platform consumes it (pin in `tools/modules.lock`), and the parent is re-pinned at the end of each part (`bash tools/check-modules-lock.sh <parent>` must say OK; the parent's `modules-lock` workflow checks it).
3. One `fault-proofs` dispatch per part, for the new or changed gates only (`ci/faults/p3/`, phase directory `p3`; module-target patches need the lock to name the module commit they apply to).
4. After every chunk: update the row (status, repo@commit, run URL), commit, push. A `CLOSED` row must cite its head (`platform@<sha>`) and its runs, or `check-verified-heads` fails.

## Rulings carried into this phase (the owner's; nothing here reopens them)

- Repositories are public, source visible, all rights reserved (owner, 2026-11-17).
- ZeroBounce stays **disabled**; its mapping follows the live status-codes page. The unknown rule stands: *"An unknown caused by the recipient's server is charged; one caused by us, or that can't be proven either way, is free."*
- Malformed addresses are rejected **before** module 1 and are free (charge row P-08); the platform normaliser implements M1's frozen `norm/v1` exactly and is the same rule the suppressions table enforces.
- The contract test of Phase 3 is run against the **real modules** in the harness (no mocks); a module that is down, slow or returns an unexpected shape yields a typed error, never an outcome.
- The Tier 4 decision (should M1 adopt quote/run/report/describe?) is the owner's; this phase supplies the evidence and a recommendation and implements nothing of Tier 4.

## Part B — Phase 3 module integration (the contract test)

Design (from the research; each decision is flagged and, where it is the owner's, listed under Open decisions):

- **Packages.** `internal/modclient` (plumbing: transport, auth, envelope, typed errors, health/readyz/vocabularies/describe where they exist, dials), `internal/adapters/m1`, `internal/adapters/m2`, `internal/adapters/m3` (thin: the module's verbs mapped to `charge.Outcome` and `money.SettleItem`), `internal/tenant` (login → platform user → module scoping). The existing `internal/m1results` becomes the core of `internal/adapters/m1` (moved, not rewritten: its tests and the live D2 test keep passing) and `internal/m3admin` stays the suspension client the adapter composes with.
- **Typed errors, never an invented outcome.** `Unavailable` (connection refused, 503 `unavailable`), `Paused` (503 `paused`: wait, not page), `Timeout`, `ContractViolation` (a shape the adapter does not recognise: status, JSON, missing key, wrong type, oversize), `Refused` (401/403/409/422 with the module's code), `NotFound`, `RateLimited`, `NotSupported` (M1 has no describe). A function that returns an error returns no value; no zero verdict is ever produced; retries are for idempotent reads only (config dials), never for M1's non-idempotent bulk POST (an unconfirmed POST is recorded as "orphan job possible").
- **Tenancy.** M2/M3: `user_id` = `public.users.id` in the body (quote/run/create/bulk) or the query (everything else) with the service token. M1: the tenant is the `user_id` of the caller key that submitted the job; one key per platform user derived as HMAC-SHA256(`PLATFORM_M1_KEY_SECRET`, "m1-caller|" + user id) and provisioned as a `verify.api_callers` row by a privileged function (the harness provisions two tenants; the production trigger is Phase 4/7) so that the module itself, not only the platform, refuses a stranger's read.
- **Harness.** (i) M1 gets a real verifier node plus fixture DNS, SMTP and an "ipify" HTTPS fixture on a second internal network whose /24 the probe-destination guard calls public (the guard stays ON; nothing in M1 is modified); promotion `UPDATE verify.nodes ... status='active', port25_open=true` after the first green audit row, small queue age/attempt dials; staged: node alone, then wired. (ii) M2 gets a worker (`m2-worker`, mTLS and KMS material generated at run time and masked), the admin key hash env, a pool and an account created through the admin API, and the existing controllable sink as its SMTP target; retry/age dials shortened. (iii) M3 as in Phase 2 plus a Domain-A token for the test container. (iv) A fault-injecting stop/start of each module for the outage proofs (`run.sh` stages, the way stage 9b stops M3).

## Open decisions (mine to record; work continues on the defaults)

1. **M3 has no cancel** (research m3-api section 0.1). Default: no module change; the platform's own rule is that M3 jobs cannot be cancelled, only paused by suspension (no new claims; queued items stay queued) and, as a last resort, drained by disabling the user's accounts (side effect on accounts). *Owner:* an additive `POST /v1/cancel` for M3 mirroring M2's, or accept the platform-side rule.
2. **M1 caller keys: one per platform user (derived HMAC, provisioned by SQL as the privileged identity) versus one service key.** Default (built in B2): one per user, so the module itself isolates tenants. *Owner:* confirm, or choose the service key and platform-only isolation. The production trigger (user creation) is Phase 4/7.
3. **`run` 409 on M3 has four indistinguishable causes** (suspended, another campaign active, campaign cap, queue cap) and quote predicts two of them wrongly. Default: the platform pre-checks from its own state (entitlement, its one-active-job rule, `quote.caps`) and treats an unexplained 409 as "refused, cause unknown". *Owner:* request additive `details[]` on that 409.
4. **M1's install documentation says a node promotes itself; the code never does** (nothing moves `provisioning` → `active` or sets `port25_open`; a control-plane restart resets both). The harness does it in SQL. Flagged as a module finding (documentation or code) in `phase-3-findings.md`; *owner:* a module change before go-live.
5. **M2 allows one active campaign per user (409)** which matches "one active job per module per user": the adapter treats the 409 as backpressure, Phase 4 owns the serialisation.
6. **The Tier 4 decision** (does M1 adopt quote/run/report/describe?). Recommendation and evidence: `phase-3-findings.md`. *Owner decides.*
7. **Where the service container gets M3's Domain-A token** (`PLATFORM_M3_SERVICE_TOKEN` next to the admin token): added as a config dial with a consumer in B5.
8. **Tier 4 evidence is in** [`phase-3-findings.md`](phase-3-findings.md) section 5: the recommendation is a PARTIAL Tier 4 for module 1 (`describe`, an idempotent job creation, totals on the job status), not `quote`/`run`/`report` parity. *Owner decides* (this is decision 6 above, now with its evidence).
9. **How strict the platform's own address check is.** Module 1 charges (M1-10) an address that normalises under `norm/v1` but fails its later syntax layer (for example `a@b`), because `norm/v1` has no length, character or dot rules. *Owner:* keep (the charge is for a check that happened) or add platform-side pre-validation before Phase 4; `Docs/install.md`'s statement that verification and the suppressions table share one rule is inexact in the same corner (the harness test `TestNormAgreement_Database` lists 22 vectors where the table's CHECK and `norm/v1` differ).
