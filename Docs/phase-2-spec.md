## Part B — Money core

### Charge rules (one pure function)

`internal/charge`: `Decide(Outcome) → Decision{Kind: Charge | Free | NotFinal | Unmapped, Unit, Rule}`. The table is **derived from module code** (three read-only reports, kept in `Docs/history/p2-research/`, every claim with a file and line) and is **data**: `internal/charge/rules.psv`, embedded and parsed, first match wins, one row per outcome. `scripts/check-charge-table.sh` fails when the block below differs from the file by one byte, so the prose cannot drift from the code; a test proves every legal module-1 status/reason pair is matched by an explicit row or by the explicit catch-all, and has one case per row.

Meaning of a decision: **charge** = one ledger charge row of that unit at the job's *frozen* price; **free** = final and not charged (no ledger row; the reserved credits come back at release); **notfinal** = not terminal, left unsettled; **unmapped** = *the module's response cannot tell us whether this is an answer or our own failure*. Unmapped is **flagged, not guessed**: nothing is charged, the item is returned to the caller in `SettleResult.Unmapped`, and the credits come back at release. It is the safe side for the customer, and it is a **module gap for the owner's ruling** (open decisions 12–14).

Outcome columns: `state` is M1's `status` or M2's item `state` (or a platform-determined class for module `platform`); `reason` is M1's reason (`*` for M2); `cache` is M1's `flags.from_cache` (never `meta.from_cache`, which is always false in bulk); `skip` is M1's `signals.smtp_skipped_reason` (`none` = absent, `capacity` = one of `no_eligible_node`, `audit_red`, `warmup_cap`, `rate_limited`).

**What does not map, and why (module gaps for your ruling — none changed from here; the module reports with file:line are in `Docs/history/p2-research/`):**
- **M1-G1** a bulk result carries **no per-item id and no address**, so a verdict cannot be attributed to an input row; the platform can only settle a *complete* job over one full paginated read, with `item_ref = <job>:<ordinal>` (stable once complete, unattributable). The P4 exit "settlement matches the module report item by item" cannot hold for M1 until M1 returns an item id.
- **M1-G2** M1's dedup is **global and permanent across jobs and owners** (`work_items.idempotency_key` UNIQUE, `ON CONFLICT DO NOTHING`): an address any tenant ever enqueued gets **no result** in a later job; the comment says "still-pending identical check", the constraint says forever. Rows 'duplicate' are never charged (no outcome exists), and the customer receives no verdict for them.
- **M1-G3** provenance: cache is readable (`flags.from_cache`); the vendor path never runs in the shipped binary (`m1_vendor` is unreachable today); own-probe versus cheap-layers is not exposed and does not matter (both are `m1_own`).
- **M1-G4** `unknown/dns_error|smtp_timeout|smtp_error|connection_failed|smtp_blocked` cannot be split into *our failure* and *a genuine answer* (rows M1-18..22): **unmapped**, proposal: M1 adds a `signals.failure_origin = own|remote` discriminator; until then they are never charged.
- **M1-G5** our capacity failures settle as `risky/plausible` with a skip token, **not** `unknown`: charged by a naive filter on `unknown`; row M1-15 catches the four tokens. **M1-G6** `risky/plausible` without a token cannot show that SMTP was unwired at boot (charged, caveat recorded). **M1-G7** some failures never settle at all (decrypt/compute errors requeue forever; no terminal state).
- **M2-G1/G2** the report has no reason or error class and a generic failure stays `queued` **with no retry cap**: a permanently failing item is never terminal, so it is never charged and the platform needs its own staleness policy (P4). **M2-G3** M2 has **no cancel route**: a platform-cancelled job leaves M2 items queued and they may still send (P4). **M2-G5** the campaign report's pagination skips one item per page boundary (settle per item, or campaigns ≤ the page size).
- The five not-charged classes of the build plan are rows P-01..P-06 and M2-03/M1-15; "M1 `unknown` from our own failure" is only partly separable (M1-G4).

### Design (what is built and why)

1. **One transaction per operation** (grant, reserve, settle, release, adjustment); the store takes an interface so the job engine (P4) can run a reserve inside its own confirm transaction.
2. **All money writers of one (user, module) serialise on one advisory lock** in the platform band, `7_000_000_000 + hash(user, module) mod 10^9`, taken first in every money transaction. The balance trigger and `CHECK (available >= 0 AND reserved >= 0)` stay as the second wall; the store's lock is what gives callers a clean `InsufficientCredits{shortfall}` instead of a CHECK error. (The roles cannot `SELECT … FOR UPDATE` the balance row — they hold SELECT only, by design — so the advisory lock is the serialiser.)
3. **Reserve** (`platform_0005`): in one transaction, with the job row locked, the module's unit prices are copied into `platform.job_unit_prices` by one `INSERT … SELECT` while `FOR SHARE` locks on the module's `unit_costs` rows hold off a concurrent price change until commit, so *the snapshot equals the table at that instant* is a fact and not a race; the reserve row freezes the **dearest** snapshot price × units. The database refuses a reserve whose rate is not the dearest snapshot price, a second reserve for one job, and a reserve with an incomplete snapshot.
4. **Settle** is idempotent **per job item by a database key**: charge rows carry `item_ref` (the module's own item id) and `UNIQUE (job_id, item_ref) WHERE kind = 'charge'`, independent of the idempotency key the code derives. A charge is exactly one unit (`units = 1`). A charge consumes the reserve **it names**, capped per reserve by `platform.reserves` (written only by the ledger trigger, `CHECK (charged + released <= reserved)`) — the pooled balance cannot hide one job spending another's reservation. Items whose outcome is `Free` write nothing; `NotFinal` items stay unsettled.
5. **Release** returns exactly the remainder `reserved − charged − released`, once (`UNIQUE (reserve_id) WHERE kind = 'release'`, amount checked by trigger against `platform.reserves`), and only for a job that has ended; zero remainder writes no row.
6. **Adjustment** removes only `available`, names an admin and a reason, and writes `admin_audit` by trigger.
7. **M3 entitlements**: `platform.m3_entitlements` is written **only** by a trigger on the ledger kinds `m3_enable` / `m3_disable` / `m3_expire` (the same single-writer pattern as the balance; "entitlement equals the last ledger event" is a test, not a gate: the drift gate stays money-only); `m3_expire` is refused by the database unless the entitlement is enabled and its `enabled_until` has passed. Delivery to M3 is separate bookkeeping, `platform.m3_sync`: the entitlement trigger raises `want_version`; **the database refuses `converged_version = want_version` unless `observed` (the state module 3 itself answered with) equals the wanted state (`m3_sync_converged_only_when_observed`)**, so the platform never reports "suspended" it did not confirm. Two platform loops run in `cmd/platform`: **expiry** (due entitlements → `m3_expire`) and **reconcile** (suspend/unsuspend through M3's real admin route; module 3 has no read route, so its POST answer is the confirmation: 200 = it changed, 422 conflict = it already was; retry with backoff until converged; periodically re-send to catch drift).
8. **Time is the database's**: expiry compares `enabled_until` with the database's `now()`, never an application clock.

### Concurrency proof (exit criterion)

A forced interleave, not hope: a test connection holds the (user, module) advisory lock; two real store reserves are started in separate sessions; the test proves **both backends are blocked** on it (`pg_stat_activity.wait_event_type = 'Lock'`, `pg_blocking_pids`), then releases it; exactly one reserve succeeds, the other returns `InsufficientCredits`, the balance is never negative, `balance_drift` is empty. The paired control runs the same interleave with both protections removed (a raw check-then-act and no `CHECK`) and **must overdraw**; the fault patch removes the lock and the CHECK from the real code and the test goes red naming `OVERDRAW`.

## Amendments to the Locked section (Phase 1 items 1–12)

Every change is a forward migration or a recorded ruling; nothing in Phase 1's section was edited, so this list is the whole difference.

- **#12 is replaced.** *Was:* a disabled admin can still be named. *Now:* **the database refuses a disabled admin** in `platform.ledger.acting_admin_id`, `platform.admin_audit.admin_id`, `platform.m3_entitlements.changed_by` and a `platform.unit_costs` price or `changed_by` change — SQLSTATE 23514, constraint name `admin_is_active` (`platform.require_active_admin`, called by four `SECURITY DEFINER` trigger functions, `platform_0004`). An **unknown** admin is still refused by the foreign key (23503). History is untouched: rows written while the admin was active stay readable. The checks take `FOR SHARE` on the admin row, so a concurrent disabling waits for the writing transaction.
- **#7 gains a kind.** The ledger kinds are grant, reserve, charge, release, **adjustment**, m3_enable, m3_disable, m3_expire. An adjustment is the clawback: admin only, a non-blank reason, `available_delta < 0` and nothing else (`reserved_delta = 0`, no job, reserve or unit), never below zero (the balance CHECK refuses the overdraw), monetary (the balance trigger and `balance_drift` cover it), and an `admin_audit` row (`ledger.adjustment`, the same admin, the reason, `credits_removed`) is written by trigger in the same transaction. `ledger.monetary` is a generated column, so `platform_0004` drops and re-adds it (and the view and foreign key that use it).
- **#4 gains a note (OD-11 ruled).** Single-label domains (`a@b`) are **accepted**, because the rule is the same for verification and suppression (module 1's frozen `norm/v1`); `a@b..c` and every other malformed form are still refused. A test pins both.
- **#13 (new) — the system user holds nothing.** The all-zero uuid (module 2's shared-pool owner, no login) can hold no balance, ledger row, entitlement or suppression (CHECKs `*_not_the_system_user`), and **`platform.listable_users` is the only sanctioned user list**; `scripts/check-user-lists.sh` fails when platform code (non-test Go under `internal/` and `cmd/`, SQL under `db/` except migrations) selects `public.users` directly.
- **#14 (new) — the active-job slot.** One active job per module per user, and *active* includes **scheduled**: the partial unique index is `jobs_one_active_per_user_module` over `scheduled`, `running`, `paused`, `cancelling` (it replaces `jobs_one_executing_per_user_module`).
- **#15 (new) — module 1 migrates through a tracker.** `verify.schema_migrations` records every migration with its sha256; module 1's own runner applies each file once, in order, refuses a changed, missing or out-of-order history, adopts a database the old psql loop already took to 0016/0017, and **never replays 0001–0015 after 0016**.
- **#16 (new) — the install runs on the image CI runs.** The required provisioning step (`db/install/preprovision.sql`) is step 2 of `Docs/install.md`; `harness` and `db-tests` run on the digest-pinned `supabase/postgres` with every migrator connecting as the non-superuser `postgres`; the integration tests' superuser is the image's own `supabase_admin`.

## Open decisions (yours)

Rulings already given are implemented and are not listed. These are new, and each has a default that is **safe for the customer**; none blocks work.

1. **M1 `unknown` outcomes that mix our failure with a genuine answer** (charge rows M1-18..22: `dns_error`, `smtp_timeout`, `smtp_error`, `connection_failed`, `smtp_blocked`). *Default (built):* unmapped = never charged, returned to the caller, the credits come back at release. *Proposal:* M1 adds a discriminator (`signals.failure_origin = own | remote`); until then they stay unmapped. *Your ruling:* keep unmapped, or rule that a class is charged (e.g. `smtp_blocked`) or free.
2. **M1 bulk results carry no per-item id or address** (M1-G1): the platform can settle an M1 job only when it is complete, over one full paginated read, with `item_ref = <job>:<ordinal>`; verdicts cannot be attributed to input rows. P4's "settlement matches the module report item by item" cannot hold for M1 until M1 adds an item id. *Your ruling:* ask for an M1 change before P3.
3. **M1's dedup is global and permanent across jobs and owners** (M1-G2): an address any tenant ever verified yields **no result** in a later job (the code's comment says "still-pending"; the constraint says forever). Customers would pay a reserve for addresses that return nothing. *Default:* duplicates are never charged (no outcome exists). *Your ruling:* this probably needs an M1 fix (tenant-scoped or time-bound dedup) before launch.
4. **`m1_vendor` is unreachable today** (M1-G3: `buildExternal` is nil in the shipped binary). The price row and the charge row exist and are tested; nothing can earn them yet.
5. **M2 retries without a cap and has no cancel** (M2-G2/G3): an item that fails permanently for a reason other than a hard bounce stays `queued` forever, and a platform-cancelled job leaves M2 items queued that may still send. *Default:* never charged (never terminal), credits released at job end. *Your ruling for P4:* a staleness policy, and whether a cancel route is requested of M2.
6. **M3's suspend is not instant and has no read route** (`Docs/history/p2-research/m3-suspend.txt`): in-flight sends (at most `concurrency_per_user`, default 3) finish after the call returns; test-send, verify-on-add and the account test button are not gated by suspension; and there is no way to read the suspended flag, so the platform treats a repeated POST's `422 conflict` as the read-back. *Default (built):* "halt" means no new claims, proven as such. *Your ruling:* ask for a read route and a suspension marker (ownership).
7. **`m3_entitlements` UPDATE refuses a row whose `changed_by` is now a disabled admin even when the update leaves it alone** (found by the Part A tests); unit costs only check on change. Part B makes entitlements ledger-written, so this is moot unless you want the same rule on unit costs.
8. **First admin: an existing inactive `public.users` row is used as is** (the command does not refuse or reactivate it).
9. **Supabase-side items stay the owner's**: the exposed-schema setting (a runner cannot see it) and the real `m1_vendor` price.

### Part B amendments (Locked items 13–20)

- **#7 again — a charge is one unit of one job item.** `ledger.item_ref` (the module's own item id, non-blank, ≤ 200 bytes) is required on a charge and forbidden on every other kind (`ledger_item_ref_shape`); `units = 1` (`ledger_charge_is_one_item`); `UNIQUE (job_id, item_ref) WHERE kind = 'charge'` (`ledger_one_charge_per_item`). *Settle is idempotent per job item by a database key*, independent of the idempotency key the store derives.
- **#5 extended — one writer for the derived facts.** `platform.balances` (Phase 1) now has two siblings that only a ledger trigger writes: **`platform.reserves`** (per reserve: reserved, charged, released; `CHECK (charged + released <= reserved)`: one job cannot spend another job's reservation even when the pooled balance could pay) and **`platform.m3_entitlements`** (below). The application roles hold SELECT only on all three.
- **#17 (new) — a reserve is whole, dearest and once.** One reserve per job (`ledger_one_reserve_per_job`); its unit cost must be the **dearest** price of the job's snapshot and the snapshot must hold a price for **every** unit of the module (`ledger_check_reserve`: `reserve_at_the_dearest_price`, `reserve_needs_the_complete_snapshot`); a release returns **exactly** the remainder `reserved − charged − released` (`release_is_the_remainder`) and at most once (`ledger_one_release_per_reserve`).
- **#18 (new) — the ledger's clock is the database's.** `ledger.created_at` is overwritten with the transaction's `now()` by a trigger (`ledger_stamp_created_at`): a writer-supplied value is ignored, so "time is the database's" is a fact for every row (found by the test author: any role with INSERT could back-date money rows or force an early entitlement expiry).
- **#19 (new) — module 3's entitlement is a ledger fact.** `m3_entitlements` is written only by the ledger kinds `m3_enable` (with `until_at`), `m3_disable` and `m3_expire`; `m3_expire` is refused unless the entitlement is enabled and its date has passed (`m3_expire_is_due`); delivery to module 3 is `platform.m3_sync`: `want_version` rises with every change of the wanted state (and the retry history resets), and `converged_version = want_version` is refused unless `observed` — the state module 3 itself answered with — equals the wanted state (`m3_sync_converged_only_when_observed`).
- **#20 (new) — money writers of one (user, module) serialise** on one advisory lock in the platform band (`internal/money.LockKey`), taken first in every money transaction and once; the database CHECKs stay the second wall.

## Open decisions (yours) — added in Part B

10. **Snapshot content is enforced by the store, not by the database.** `job_unit_prices` is checked for completeness and dearest-of-itself, but a role holding INSERT could forge a snapshot price (for example the vendor price as 1) that differs from `unit_costs`. "The snapshot equals the table at that instant" is a database fact only through `internal/money` (`FOR SHARE` on the price rows, proved blocking by `TestMoneyStore_SnapshotEqualsTheTableAtThatInstant` with a fault leg). A trigger comparing each snapshot row with `unit_costs` would close it; it would also force every Phase 1 test that fabricates a price to change. *Default:* store-enforced, recorded here. *Your ruling:* add the trigger before launch?
11. **Terminal job states are not final in the database** (`jobs_guard` lets `succeeded` go back to `draft`). `Release` and the settle checks assume a terminal job stays terminal. A transition trigger belongs to Phase 4 (the lifecycle); until then the store refuses what it can (`Release` needs a terminal status, `Reserve` a draft one).
12. **The convergence wall is "observed matches", not "observed after this version".** The code guards freshness with a compare-and-set on `want_version` and `want_suspended`; the database CHECK only ties the recorded state to the wanted one. An `observed_version` column would make the freshness a database fact too. *Default:* the CAS (tested by `TestEntReconcile_AStaleAnswerNeverMarksTheNewVersionConverged`).
13. **A scheduled job holds the slot but nothing yet moves a job there.** Reserve leaves the job in `draft`; the confirm transaction that sets `scheduled` or `running` is Phase 4's (`ReserveIn` lets it run inside that transaction).
14. **A positive correction is a grant.** `adjustment` can only remove available credits; there is no kind that restores credits except a `grant` by an admin.
15. **The one exception to the empty `.gitleaksignore` / no-leak rule** (`.gitleaks.toml`, commit `355299a6`): a placeholder SMTP-sink password literal (`"smtp_secret": "m3-live-harness"`) in the live module-3 test tripped `generic-api-key` after it was pushed. I did **not** rewrite history (no GitHub deletions this phase) and did **not** loosen the empty-ignore-file gate: one `[[allowlists]]` block, one rule, one immutable commit, plus `scripts/check-gitleaks-config.sh` (24-case selftest, a fault leg) that fails on any other shape of exception. *Your ruling:* keep it, or have the two commits rewritten.
