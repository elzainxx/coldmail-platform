# Installing the platform on Supabase

This is the install procedure, in the order it must be run. Every command below is the command CI runs against the digest-pinned `supabase/postgres` image (the `harness` workflow runs steps 2–4 as a real install does; `scripts/check-install-doc.sh` fails when this document names a file, command or setting that no longer exists). What CI does **not** run is stated at the end ("Not checked").

The platform and the three modules share one Supabase Postgres database, each in its own schema: `platform` (the platform), `verify` (module 1), `send_managed` (module 2), `send_byo` (module 3), plus the platform's two tables in `public` (`users`, `job_items`) that modules 2 and 3 read.

## Step 1 — the Supabase project

Create the project and note the **database** connection string of the migrating role `postgres` (not a superuser on Supabase: that is why the steps below exist). Keep Supabase Auth's email + password sign-in on and **public sign-up off** (locked decision: users are created by an admin). The `auth.users` table must exist: `platform_0001` refuses to run without it.

## Step 2 — required role provisioning (`db/install/preprovision.sql`)

Run once, as `postgres`, **before any module migrates**:

```
psql "$MIGRATE_DATABASE_URL" -v ON_ERROR_STOP=1 -f db/install/preprovision.sql
```

Why: on PostgreSQL 16 and later the creator of a role holds only `ADMIN OPTION` on it, with neither `SET` nor `INHERIT`, so `postgres` cannot create objects as the owner roles of modules 2 and 3 and their own migrations stop with `42501` (measured on every run by the `supabase` workflow's BASELINE leg: exactly eight statements fail without this step, and none with it). The file creates `send_managed_owner` and `send_byo_owner` if missing and grants both to `postgres` `WITH INHERIT TRUE, SET TRUE`. It is idempotent and changes no module.

## Step 3 — migrations, in this order, all as `postgres`

1. **Platform**: `platform-migrate up-and-set-password` (`PLATFORM_MIGRATE_DATABASE_URL`, `PLATFORM_MIGRATIONS_DIR=db/migrations`, `PLATFORM_APP_PASSWORD`); see [`migrator-reference.md`](migrator-reference.md). It creates `public.users` and `public.job_items` before any module needs them.
2. **Module 1**: its migrations, then the runtime password out of band (`ALTER ROLE verify_app PASSWORD …`), per the module's own install notes. Then run **step 3b** below (it needs module 1's schema and nothing of modules 2 and 3, so it may run before or after their migrations).
3. **Module 2** and **module 3**: each module's own migrator (`up-and-set-password`), with its own `MIGRATE_DATABASE_URL`. Their pre-flight (`check_platform_tables.sql`) passes only after step 3.1.

## Step 3b — after module 1's migrations: `db/install/postmodule1.sql`

Run once, as `postgres`, **after module 1's migrations** (step 3.2), and before the platform serves a module 1 job:

```
psql "$MIGRATE_DATABASE_URL" -v ON_ERROR_STOP=1 -f db/install/postmodule1.sql
```

Why: module 1 has **no API that mints a caller key**. Its tenant is the user of the key that submits a job, and `verify.api_callers` is written only by module 1's own privileged identity. The platform service runs as `platform_app`, which has no right on module 1's schema and must **never** hold module 1's admin credential. The file therefore creates exactly one function, `platform.provision_m1_caller(user uuid, key digest bytea)`: `SECURITY DEFINER`, owned by module 1's grant-admin role `verify_admin`, `search_path` pinned to `pg_catalog, pg_temp`, executable by `platform_app` and **nobody else** (`REVOKE ALL … FROM PUBLIC`; the grants converge on every run, so whatever the image's default privileges added is taken back, and the file proves its own effect at the end). It inserts one kind of row (`caller_id` = `platform-user-` plus the user's id, a start an hour back, no expiry, the user as owner; `ON CONFLICT (key_sha256) DO NOTHING`), reads the row for the digest back, and **raises** when that row belongs to another user, has no owner, or is outside its validity window, so a hand-made ownerless key is never hidden by the silent "do nothing". It refuses a NULL user, the all-zero system user and a digest that is not 32 bytes. It cannot update or delete anything.

From then on the **platform service registers a user's key itself, at the user's first module 1 job** (`internal/tenant` `M1CallerEnsurer`, called by the job engine; once per user and key version per process, idempotent, a restart simply calls it again): there is **no per-user operator step**. After a key rotation (`PLATFORM_M1_KEY_VERSION` and the secret moved, `config-reference.md`) the first job of each user registers the new version's key beside the old one through the same function; **ending** the old key stays an operator action through the privileged identity (`RetireM1CallerVersion`), because the function cannot update a row.

How it runs as the non-superuser `postgres` (the same constraint as step 2): on PostgreSQL 16 and later the creator of a role holds only `ADMIN OPTION` on it, so the file grants `verify_admin` to the migrator `WITH INHERIT TRUE, SET TRUE`, exactly as `db/install/preprovision.sql` does for the send owners; then, in **one transaction**, it gives `verify_admin` `USAGE` and `CREATE` on schema `platform` (the one role that may write module 1's table has to own the function, and creating a function in a schema needs `CREATE` on it), creates the function as that role, sets its grants, and takes both schema privileges back. Any failure rolls the temporary grants back with everything else. The file is idempotent and re-runnable (`CREATE OR REPLACE`, a membership granted only when missing, grants that converge), and every statement is schema-qualified; no module is changed and module 1's tables and grants are untouched.

What it adds to the threat model: nothing the service lacks. `platform_app` already holds the key-derivation secret (`PLATFORM_M1_KEY_SECRET`), so it can compute every user's key and already acts as any user at module 1; the function removes the need for module 1's **admin** credential in the service, whose reach is every table of module 1. What a compromised service could still do through it is to register a key of its own choosing for a user id and to add rows without bound; it cannot change or remove a row, register a key with no owner or for the system user, or choose another `caller_id`.

CI runs this step exactly as an install does: the harness (stage 4) runs it as `postgres` right after module 1's migrations, **twice** (the second run must leave the function and the schema's privileges as the first left them), the `supabase` workflow's FIXED leg runs it as `postgres` after module 1's chain on the pinned image (`tests/supabase/run.sh --postmodule1`), and the full harness's `TestM1LiveProvision_*` tests (`tests/harness/m1_provision_test.go`) prove who may execute the function, that `platform_app` cannot write module 1's table itself, that a registered key authenticates at module 1's real front door as that user and nobody else, and that a planted ownerless row is refused and left unchanged. A deployment that skips this step fails the provisioning of its first module 1 job with `platform.provision_m1_caller does not exist`, an error that names this step.

## Step 4 — the first admin

An admin is a Supabase login with a row in `platform.admins`. Create the login first (Supabase dashboard → Authentication → Users), then:

```
platform-migrate create-first-admin --auth-user-id <the login's id> --display-name "<name>"
```

It creates the `public.users` row and the `platform.admins` row in one transaction, as the privileged migrating identity, and **refuses when any admin already exists** (admin management is built in Phase 7; until then more admins are added out of band by the owner). It refuses an unknown login, a blank name and the all-zero system user, and it refuses a login whose platform user already exists and is **inactive** (reactivate that user first, or use a different login; the command never reactivates anyone).

## Step 5 — remove the platform's schemas from the exposed API (owner action, Supabase dashboard)

In Supabase → Settings → API → *Exposed schemas*, **remove `public` (and never add `platform`, `verify`, `send_managed` or `send_byo`)**. The platform's tables are reached only by the Go service over the database connection, never through PostgREST. `platform_0001` already revokes `anon`, `authenticated` and `service_role` on `public.users` and `public.job_items`; **no row-level security is enabled** (ruling: the exposed-schema setting and the revokes are the control, and a second mechanism would be a second place to be wrong). The same line is in the parent repository's `OWNER-ACTIONS.md`.

## Settings an admin owns

- **Unit costs** (`platform.unit_costs`): five units, integer credits ≥ 1. The seed is `m1_own` 1, `m1_cache` 1, `m1_vendor` **2**, `m2_accepted` 1, `m2_bounced` 1. The vendor-fallback price (`m1_vendor`) is an **admin setting** and must stay above 1; the seed of 2 is a placeholder the owner replaces before launch. Changing a price needs a named admin and a reason and is recorded in `platform.unit_cost_history`; a job freezes its prices at confirm, so a change never affects a job already confirmed.
- **Module 3** is not metered: an admin enables it per user, optionally until a date.

## Module 1's vendor fallback (ZeroBounce) — ships disabled

The platform charges a vendor answer as `m1_vendor` (the unit price above), but the vendor itself is **module 1's** and is switched on in module 1's environment, and **the platform has no setting for it**: module 1 says whether it is on, and the platform reads that. Everything in the table is module 1's own configuration (`coldmail-verify/Docs/vendor-zerobounce.md` is the reference, section 2a; the owner steps, in order, are section 3 of the parent repository's `OWNER-ACTIONS.md`). Nothing is sent to the vendor until **all** of the switches are on:

| Dial (module 1) | Default | What it does |
|---|---|---|
| `TM_FALLBACK_MODE` | off | `enabled` allows the external-fallback stage (the global kill switch can still force it off) |
| `TM_EXTERNAL_DPA_CONFIRMED` | false | `true` only after the vendor's data-processing agreement is signed |
| `TM_EXTERNAL_ZEROBOUNCE_KEY_ENV` | `ZEROBOUNCE_API_KEY` | the **name** of the environment variable that holds the API key (the key itself is never in a file or a repository) |
| `TM_EXTERNAL_DAILY_SPEND_CAP` | 0 | credits per UTC day module 1 may spend at the vendor; 0 sends nothing |
| `TM_EXTERNAL_ZEROBOUNCE_TIMEOUT_MS` | 8000 | per-call timeout, 3000–60000 |
| `TM_EXTERNAL_ZEROBOUNCE_BASE_URL` | `https://api.zerobounce.net` | the vendor endpoint (a regional host if the owner chooses one) |

**How the platform learns the state.** Module 1's `GET /v1/describe` carries `vendor_fallback.reachable`: `true` only when every switch its external stage needs is on **at that moment** (the fallback mode, the DPA confirmation, the key present in the variable the key dial names, a daily spend cap above 0, the policy opting in, the kill switch not pulled); module 1 computes it per request from the very predicate its stage is wired from, so the answer and the stage cannot disagree. The platform reads it **before the transaction of every module 1 preview and confirm** (never an HTTP call under a lock; the answer is kept for 5 seconds) and writes it into `platform.unit_costs.reachable` for `m1_vendor` through the audited function `platform.set_unit_reachable` (source `m1_describe`; nothing is written, not even a history row, when the flag already says so). So the owner switches **module 1's `TM_EXTERNAL_*` dials and nothing on the platform** (the variable the platform once had for this is removed: a deployment that still sets it gets one warning at start-up naming it, and it changes nothing; [`config-reference.md`](config-reference.md), "Removed variables"). What the flag decides is what a **module 1 job reserves**, because a reserve holds credits at the dearest unit a job of the module can be charged:

- **Reachable `false` (module 1's default):** `m1_vendor` is not reachable, a module 1 job reserves **1 credit per row**, and a vendor answer that arrives all the same is never charged: the settlement returns it as unmapped, with the charge rule that decided it, and its credits stay in the reserve until the release.
- **Reachable `true`:** a **new** module 1 job reserves **2 credits per row**, and a vendor answer is charged `m1_vendor`.
- **A preview made under the other answer is stale.** The fingerprint of a preview holds the prices of the reachable units, so a confirm whose preview was made while the flag said the other thing is refused `409 preview_stale`; the user previews again and sees the new rate (`unit_cost`, `credits`).
- **A job already confirmed never changes.** Its prices were frozen when it reserved: a flip of module 1's switches moves no existing job, in either direction (a job reserved with the vendor on can still be charged for a vendor answer after it is switched off).
- **Every instance reads it too.** Each platform instance, leader or standby, runs a loop that reads module 1's describe when it starts and every 60 seconds (every 5 seconds until the first success; it needs neither the database nor module 1 to start) and writes the flag the same way, so the flag follows module 1 even when nobody previews anything. The write is idempotent, so any number of instances do no harm. `platform.unit_reachability_history` records every change with its source.
- **When module 1 cannot be read** (it is down, it refuses the platform's key, or it is an older module 1 whose describe has no `vendor_fallback`) nothing is written and nobody is told the stored flag is fresh: the preview carries `vendor_reachable_known: false`. The rule for a confirm is the customer-safe one, a reserve at the dearest price and never an uncovered one: a stored `true` is kept (the job reserves 2 per row and the rest is released at the end); a stored `false` that module 1 itself set (source `m1_describe`) is kept; and the one case that is **refused** is an *immediate* confirm while the flag is off and was **never set by module 1** (the seed of 1 credit per row, or a value an earlier build wrote from its own configuration): it answers `503 module_unavailable`, nothing is held, and the user tries again once module 1 answers. A **scheduled** confirm ignores an unreadable module 1 (it may be back by the start) and keeps the stored flag. The exact rule is in `internal/jobs/vendor.go` and is tested there and in `TestJobsStore_VendorReachabilityFromTheModule*`.
- **The platform's own caller at module 1.** Reading describe needs a module 1 caller key, and module 1 has no service credential, so the platform keeps one **service caller** of its own: a reserved id that is never a customer, whose key is derived from `PLATFORM_M1_KEY_SECRET` and `PLATFORM_M1_KEY_VERSION` exactly like a customer's and is registered at its first use through the same function as every customer's (`platform.provision_m1_caller`, step 3b above): no operator step, and a rotation of the key version re-registers it with the rest. Without `PLATFORM_M1_URL` and `PLATFORM_M1_KEY_SECRET` the platform reads nothing, refuses nothing for this and keeps the flag it holds.
- The platform side is covered by tests against a real Postgres (`TestMoneyReachable_*`, `TestJobsStore_VendorReachabilityFromTheModule*`), by the unit tests of the loop, the provider and the adapter, and by the harness scope `jobs` (stage J6), which switches a real module 1's dials off, on and off again and reads the rate each preview and confirm reserves at. **Not checked** here: a real vendor call, and module 1's behaviour when its dials change without a restart (it has no hot reload: a change of a dial is a restart of module 1, which the platform sees as soon as describe answers again).

A vendor *answer* reaches the platform as `risky` or `invalid` with reason `external_verified` and is charged `m1_vendor`; a vendor *non-answer* (an error, a timeout, an `unknown`) leaves module 1's own result standing and is charged by the ordinary rows, never as a vendor call. Not checked: any real vendor call, and the vendor's real status vocabulary (the mapping was built from its official SDKs; the owner verifies it against the live documentation first).

## Behaviours that are rulings, not accidents

- **Module 1's readiness is all-or-nothing on `TM_QUEUE_ADDR_KEY`.** Without the key `/readyz` reports not-ready and names the key. The platform always submits bulk jobs, so a deployment of module 1 without the queue can never serve the platform; a verify-only mode is deliberately not offered.
- **One address rule, in Go, for verification and suppression: `norm.Validate`** (`internal/norm`): module 1's frozen `norm/v1` normalisation, then module 1's own syntax layer exactly as module 1 implements it (after normalising, the local part is at most 64 bytes, the domain at most 255 bytes, and the domain holds a dot). An address that fails either half is never sent to a module, is counted and skipped, and is free (charge row P-08); module 1's own `invalid_syntax` answer (row M1-10) is therefore unreachable from the platform. The suppressions table stores what `Validate` returns and its CHECK (`suppressions_email_norm_v1`, `platform_0009`) is **the same rule where SQL can express it, and stricter or wider only where listed**: stricter on a NUL, white space in the local part, an empty label or a leading dot in the domain and an address over 254 bytes (an address of that kind is refused at the table although the validator accepts it; the writer treats SQLSTATE 23514 as "cannot be stored"), wider only on a punycode label that is not valid punycode (SQL cannot decode it; the writer validates first). **For those two shapes (`xn--a`, `xn--zzzzzzzz`) the Go validator is the ONLY wall**: the table would store them if they reached it, and the owner accepted that limit (Phase 4, Part A item A2) on one condition, that it is a gate. So **`internal/suppress` `Add` is the one place that writes `platform.suppressions`**: it calls `norm.Validate` first, stores the normalised form `Validate` returns (never its argument), reports a duplicate as "not created", and returns the table's own refusals as typed errors (SQLSTATE 23514 on `suppressions_email_norm_v1`, and 22021 for a NUL, are "cannot be stored"; the error never carries the address). `scripts/check-suppression-writers.sh` fails when any other non-test Go file under `internal/` or `cmd/`, or any SQL under `db/` outside `db/migrations/`, writes the table (INSERT, UPDATE, DELETE, TRUNCATE, COPY, MERGE), when a migration writes a row without a reasoned entry in `tests/suppression-writer-exceptions.txt`, and when a write in `internal/suppress/store.go` is not preceded by a `norm.Validate(` call in the same function (its fault proofs are in `ci/faults/p4a/`; the gate reads source, so SQL assembled by string concatenation, and everything under `tests/`, are not checked). `TestNormAgreement_Database` pins every difference by vector name against the real table, and the shared vector file runs through both implementations. **This supersedes the Phase 2 ruling OD-11** (single-label domains such as `a@b` were accepted): `a@b` fails module 1's layer, so it is neither sent nor stored. An earlier version of this paragraph said the two rules were identical; they were not (22 vectors differed).
- **The platform's migrations run before the modules'.** Since the Phase 3 close-out the shared table `public.job_items` carries one more nullable column, `rendered_text` (the optional plain-text part, `platform_0010`); modules 2 and 3 read it, and each refuses to migrate against a database that lacks it (its own pre-flight), so a module whose migrations ran before the platform's would stop with a message that names the column. The order of this document (platform chain first, then the three modules) is therefore a requirement, not a habit.
- **Module 1's node promotes itself.** A verifier node is `provisioning` with `port25_open=false` at every control-plane boot and becomes `active` only because a green audit recorded after that boot says so (module 1's own watcher; `port25_open` is taken from that audit). Nobody runs SQL to promote it, and a restart re-audits and re-promotes: it never trusts an `active` left behind by an earlier boot. What a green audit needs from its environment is in module 1's `operator-runbook` section 5.1. Module 1's audit does not itself open port 25 to a real mail host: the owner's egress smoke test (OWNER-ACTIONS, G1.3) stays the gate before real verification traffic.
- **Module 3's SMTP host allowlist stays empty in production.** Module 3 refuses an SMTP host that is, or resolves to, a loopback, private, link-local or cloud-metadata address (and the other special-use ranges) at add time and at connect time. The one dial that lets a private network through (`smtp_host_allow_cidrs`) exists for the harness's compose network; the module logs a loud warning at every start while it is not empty. Module 3's From-gate (`from_gate_mode`) stays `enforce`, its seeded value.
- **A scheduled job holds the one-active-job slot** for its module and user.
- **A disabled admin can no longer act**: the database refuses one in the ledger, the audit log, M3 entitlements and unit costs.

## Running more than one instance

The platform may run as several instances against one database (a rolling restart, a second node for availability). **Every instance serves HTTP; the two background loops run in exactly one of them.** The loops are the **expiry** of module 3 entitlements and the **reconcile** with module 3's suspend route. The instance that runs them is the **leader**; the others are **standbys**: they idle both loops (no pass, no call to module 3, no write), ask again at every tick, and take over when the leader is gone.

- **How the leader is chosen.** The leader is the instance that holds one PostgreSQL *session-level advisory lock*, key `7200000002` (in the platform's `7_xxx_xxx_xxx` band; the migrator holds `7100000001` while it runs). It is taken with `pg_try_advisory_lock`, which never waits, on **one dedicated connection** that the leader keeps for as long as it leads, so **one connection of the pool is checked out for that** (the pool's default is at least four). PostgreSQL frees a session lock the moment its session ends: a leader that crashes, is killed, loses its connection or is stopped hands the lock on without any lease, heartbeat or clock. A planned stop (SIGTERM) unlocks explicitly and returns the connection before the pool closes, so a standby takes over at its next tick instead of when the server notices a closed socket.
- **How long a takeover takes.** One tick of the standby's loops: the shorter of `PLATFORM_ENTITLEMENT_EXPIRE_INTERVAL_SEC` (default 30) and `PLATFORM_M3_RECONCILE_INTERVAL_SEC` (default 5), so about 5 s by default. The new leader's first pass of each loop is at that loop's own next tick.
- **One loop runs in every instance, not only in the leader's:** the reachability sync reads module 1's describe and writes `vendor_fallback.reachable` into the database (see "Module 1's vendor fallback" above). It is idempotent, and every instance writes module 1's one answer, so any number of instances do no harm and there is nothing to keep equal between them.
- **Name each instance.** Set `PLATFORM_INSTANCE_ID` to a different value on every instance (1 to 63 printable ASCII characters; the default is the host name, which is already distinct per container). The leader's lock session carries it as its `application_name`, and the election's log lines carry it as `instance`.
- **How to see the leader.** In SQL, as a role that can read `pg_stat_activity` (an admin of the database; exactly one row means one leader):

```
select a.application_name as leader, a.pid, a.backend_start
from pg_locks l join pg_stat_activity a on a.pid = l.pid
where l.locktype = 'advisory' and l.granted and l.objsubid = 1
  and ((l.classid::bigint << 32) | l.objid::bigint) = 7200000002;
```

  No row means no instance can reach the database (or all are starting). In the logs: `loops: this instance is now the leader`, `loops: another instance holds the leader lock; ...` (the standby, once per stretch) and `loops: this instance lost the leader lock; ...` (a leader whose session failed: logged once, at warn; it tries again at the next tick, like a standby).
- **The connection string must keep one backend for the whole session.** Use the direct connection or a **session-mode** pooler for `PLATFORM_DATABASE_URL`, not a transaction-mode pooler (the same reason the migrator needs the direct connection: [`config-reference.md`](config-reference.md)). Behind a transaction pooler the lock would be taken on a backend the connection does not keep; the leader checks every tick that its own backend holds the lock and gives the leadership up when it does not, but the lock could stay held on the pooler's server connection and no instance could lead until that connection closes.
- **What the lock does not promise.** A pass that is already running when its instance loses the lock runs to its end (bounded by its own timeout) while the next leader may have started; the ledger's unique keys (an expiry is one `m3_expire` row per user) and the reconciler's compare-and-set on the wanted version, not the lock, are what keep that safe. A leader that is cut off from the database but not killed keeps its server-side session, and so the lock, until the server decides the peer is gone (TCP keepalive): nothing runs twice, a takeover is late.
- **No collision of keys.** The money store and the entitlement writers take a transaction-level lock per (user, module) hashed into the same band; the hash steps over the platform's own constant keys (this lock and the migrator's), so a user's key never equals the leader's and the leader's session lock can never make a user's writes wait (a unit test in `internal/money` and one in `internal/entitlements` pin it).
- **What CI proves.** `TestLeader_*` (database tests, two real instances over one database: exactly one runs passes, the server shows exactly one granted lock held by the leader's `application_name`, a terminated leader session is replaced within ten seconds, twenty startup races never give two leaders, a stopped leader returns its connection) and the harness stage 9c in `tests/harness/run.sh` (two platform containers, the leader killed, the killed one restarted as a standby); the fault proof `loops-leader` shows the first of these red when the election is removed.

## Authentication of the job API

The job API accepts the access token Supabase gives a signed-in user (`Authorization: Bearer <token>`) and nothing else. What to set on the platform service, from the Supabase project's own settings (the full table is [`config-reference.md`](config-reference.md)):

- **A project with asymmetric signing keys (new projects):** `PLATFORM_JWKS_URL=https://<project-ref>.supabase.co/auth/v1/.well-known/jwks.json`. The service fetches the public keys from there (https only, at most every 30 seconds) and verifies ES256 and RS256 tokens with them.
- **A project on the legacy shared secret:** `PLATFORM_JWT_SECRET` is the project's *legacy JWT secret* (Supabase dashboard, project settings, JWT keys), used exactly as shown (at least 32 bytes, printable ASCII, no spaces). It verifies HS256 tokens. **Never put the secret in a file that is committed**: give it to the service through the environment or the host's secret store, like `PLATFORM_DATABASE_URL`.
- **Both may be set** while a project moves from one to the other; each token is judged by the source of its own algorithm.
- **`PLATFORM_JWT_ISSUER=https://<project-ref>.supabase.co/auth/v1`** pins the issuer. It is optional only so that the service starts without it: set it.
- `PLATFORM_JWT_AUDIENCE` (default `authenticated`, what a signed-in user's token carries) and `PLATFORM_JWT_LEEWAY_SEC` (default 30) normally stay as they are.
- **Nothing set** means the service starts and the job API is not served; the start-up log says `job API authentication is not configured`. An invalid value (a secret under 32 bytes, an `http://` JWKS URL, a leeway over 300) stops the process with exit status 2 and a message that names the variable and never its value.

The token proves who the user is and nothing more: the API resolves its `sub` to a platform user, and an inactive or unknown login is refused. Not checked here: a real Supabase token (the harness mints its own with a per-run key until GoTrue joins it, Phase 4 chunk B15), the project's key rotation (a rotated-in key verifies from the first token that names it at least 30 seconds after the previous fetch of the key set (a token that names it sooner is refused, and the user signs in again or retries); a withdrawn key stops verifying within an hour), and a signed-out session (an access token stays valid until its `exp`, normally an hour).

**When the platform cannot check a token: `503`, code `auth_unavailable`, `Retry-After: 30`.** A bad token (forged, expired, not yet valid, for another audience or issuer, `alg: none`, an algorithm other than ES256, RS256 and HS256, or malformed) is always the one `401 unauthenticated`, whether or not the key endpoint answers. When the platform cannot obtain the keys it needs to judge a token, nothing was refused, so it does not blame the user:

- **When it happens.** The JWKS endpoint cannot be reached, does not answer within 10 seconds, answers an error status or a redirect, answers something that is not a usable key set, or presents a certificate the platform does not trust, **and** the token needs a key the platform does not hold: the key set was never fetched, or the token names a key id the loaded set lacks while the last fetch has failed. The answer is `503` with the code `auth_unavailable` and `Retry-After: 30` (the key set is fetched at most every 30 seconds, so a retry sooner meets the same answer). The body is the platform's error envelope with a fixed message and says nothing of the cause (no address, no key id). Users simply retry.
- **What it does not touch.** An HS256 token is judged by `PLATFORM_JWT_SECRET` alone (accepted, or the `401`) and the key endpoint is never asked for it, so a deployment with no `PLATFORM_JWKS_URL` never answers `auth_unavailable`. A token signed by a key the already loaded set holds keeps verifying while the endpoint is down (a held key is used even past the hour the key set is trusted, until the endpoint answers again, which is also when a withdrawn key stops verifying). A token that is bad without any key (malformed, `alg: none`, a disallowed algorithm, expired, for another audience, issuer or subject) is the `401` even while the endpoint is down.
- **The one `401` that is not an outage.** A token that names a key id the loaded key set does not hold, when that set was fetched successfully less than 30 seconds ago: the platform will not fetch again that soon, so it cannot know the key was just published, and the user signs in again or retries after 30 seconds (as for a freshly rotated-in key).
- **For the operator.** The platform writes ONE warn line per stretch of unavailability, `authentication is unavailable: the signing keys cannot be obtained`, with `reason=signing_keys_unavailable` and `class=` one of `unreachable` (refused, no route, name not resolved), `timeout`, `certificate` (its certificate is not trusted), `bad_status` (an error status or a redirect), `unreadable` or `bad_key_set` (not a key set), under the request id of the first request that met it; no further line is written until the key set has been fetched again and fails again (every `503` is still in the access log, which warns on every status of 500 or more). The line holds no address and no key id: from the platform's own host, reach the host named by `PLATFORM_JWKS_URL` (DNS, firewall, the server's certificate) and check the Supabase project's status.

**The routes the token opens, and the limits that bound them**, are in [`jobs-api.md`](jobs-api.md): the thirteen routes of `/v1/jobs`, every error code, the CSV format and its escape rule, the idempotency rule of a confirm. Three optional dials bound a job and its API (all in [`config-reference.md`](config-reference.md), each with a default that needs no change): `PLATFORM_JOB_MAX_ROWS` (the longest list one job holds, default 100000), `PLATFORM_JOB_MAX_START_DELAY_MIN` (how long a confirmed or scheduled job may wait for the engine before it expires and its credits are released, default 30) and `PLATFORM_RESULTS_PAGE_MAX` (the largest page of results, default 1000). With no key source set the routes are not mounted at all: a request for one is the `404` of any unknown path, and the start-up log says `job API authentication is not configured`; with one it says `job API mounted`. The API serves no CORS headers: put the web app on the API's own origin, or behind a proxy that adds what it needs.

## Running the job engine

The job engine is what carries a confirmed job to its end: it hands the job's rows to the module, reads what the module reports, records and charges every finished item, completes the job and gives back the credits it did not use. It runs inside the platform service, in the same process as the entitlement loops, and it is on by default.

- **Leader only.** The engine runs under the SAME leader lock as the two entitlement loops ("Running more than one instance" above): in exactly one instance, the leader; a standby asks the lock at every tick and does nothing else, and takes over when the leader is gone. Nothing needs configuring for that. On a planned stop the engine ends FIRST (a step in flight ends with it), then the entitlement loops, which give the lock back, then the database pool closes. Every step of the engine is idempotent and runs under the per-user, per-module money lock, so a leader that is deposed in the middle of a step and a new leader that repeats it cannot submit or charge an item twice.
- **One configuration for all instances.** Give every instance the same `PLATFORM_JOB_*` values and the same module URLs and tokens: whichever instance leads is the one that runs the engine, and an instance with the engine off (`PLATFORM_JOB_ENGINE_ENABLED=false`) that wins the lock holds every job where it is until it is restarted or another instance leads. The engine's dials are in [`config-reference.md`](config-reference.md) ("The job engine's dials"); the defaults need no change.
- **It needs the modules.** Module 1 jobs need `PLATFORM_M1_URL` and `PLATFORM_M1_KEY_SECRET` (each user's own key is derived from it and registered with module 1 at the user's first job, once, by the privileged function of `db/install/postmodule1.sql`: the install must have run that file after module 1 migrated). Module 2 jobs need `PLATFORM_M2_URL` and `PLATFORM_M2_SERVICE_TOKEN`; module 3 jobs need `PLATFORM_M3_SERVICE_TOKEN` (and `PLATFORM_M3_URL`, which the platform always has). A module whose dials are unset is not an error: the start-up log names which adapters were built, and a job of a module that is not configured waits and goes stale. With module 3 configured, a confirm of a module 3 job also asks module 3's own quote whether the campaign can run (`module_unavailable` when it cannot be asked, the module's causes when it can and says no).
- **A module that is down never fails a job.** A module that is unreachable, slow, paused by its operator, rate limiting or answering something the platform does not understand leaves the job exactly where it is: a confirmed or scheduled job is offered to the module again at every pass until its start deadline (`PLATFORM_JOB_MAX_START_DELAY_MIN`), after which it expires and its reserve is released, free; a running job's polling halts, no outcome is invented, and the job completes once, after the module is back. A module that refuses the job for good (its own validation) while it holds none of the job's rows fails it: the rows nobody settled are free and what was charged stays charged. One that refuses after it already holds rows of the job (a later batch of a send job) does not fail it, because the module goes on with the rows it holds and they must be recorded and charged: the engine writes one `flag` job event (the module's code word only), keeps observing, and the job goes stale like any job that cannot go on; an administrator decides. A platform credential that a module refuses (a wrong token, a key version that was not provisioned) is the platform's configuration and waits like an outage.
- **The staleness alert.** A running job that makes no progress (no row handed over, no result recorded) for longer than its module's dial (`PLATFORM_JOB_STALE_AFTER_MIN_M1`, `_M2`, `_M3`; 30, 15 and 15 minutes by default) gets a `stale` job event, and another at most once per that long. The job is not touched: it is never failed or expired for being slow. Watch for the event (`platform.job_events`, kind `stale`) and for the log line `a job made no progress for longer than its module's limit`; an administrator decides.
- **A limit to know.** Module 1 takes a job's whole list in one request, so the engine reads, hands over and stamps a module 1 job's rows in one call of at most 100000 rows (module 1's own limit for one job, and the highest `PLATFORM_JOB_MAX_ROWS` accepts): every job the service creates fits, and none waits for want of a bigger call. Modules 2 and 3 are handed their rows in small batches (`PLATFORM_JOB_SUBMIT_BATCH`).
- **Which job is looked at first, and what a job that makes no progress costs.** A pass looks at the jobs that are DUE, at most a hundred, the one that has been due longest first. A pass that makes no progress on a job (its module is down, paused or full: nothing handed over, nothing recorded) puts that job off: for one pass, then two, four, and so on up to `PLATFORM_JOB_BACKOFF_CAP_SEC` (60 seconds by default, and never more than a quarter of the module's staleness limit; the database itself refuses a wait of more than 600 seconds). So a hundred jobs whose module is down cannot use every pass and keep a newer job waiting, a module that comes back is polled again within the cap, and a stale job is still noticed within it. A job someone moves (the user's cancel, an administrator) or that makes progress is looked at at the next pass; a start deadline is acted on when it comes and the release of an ended job's reserve does not wait, whatever the backoff. The wait is kept in the job row (`next_poll_at` and `idle_polls`), so a restarted engine or the next leader resumes it. Proved against a real database by `tests/harness/jobs_engine_schedule_test.go` (150 jobs whose module never answers and one new job: the new job is submitted by the next pass, and the same arrangement without the engine's memory starves it).
- **The module-facing rows are written once.** For a module 2 or 3 job the engine writes one `public.job_items` row per pending row of the list at the job's first pass, in one transaction, and records that on the job (`items_ensured_at`, set once): a pass over a job whose module is down, a later pass and a restarted engine write nothing. A job that EXPIRES, is CANCELLED before it started or FAILS gives the items of the rows no module was ever given the terminal marker `status = 'cancelled'` in the transaction that ends it (`pending` is what the platform and module 3's test-send write; nothing is deleted, the roles cannot, and an item of a row that was handed to the module or that the module answered for keeps its status). What the marker means for the modules is the next section.
- **Pause, resume and cancel of a running job: what the engine calls, and when.** (The wrappers over the adapters are `internal/jobengine/module_sendapi.go` and `module_m1.go`; the user-facing words are in [`jobs-api.md`](jobs-api.md), "Pause, resume and cancel of a running job".) Everything is LEVEL-TRIGGERED: a restart, a second instance or a crash between the user's move and the module call finds the same action, and every call is idempotent.
  - **A job `paused` while it was running** (modules 2 and 3; the database's capability row `platform.modules.can_pause`): at every look the engine reads the module's campaign report; when the report's own `paused` is false and the campaign is not complete it calls `POST /v1/pause` (idempotent) and reads the report again, and it keeps asking at every look until the report says `paused`. It never takes the answer of the call for the state, and it reads no `state` word and no `changed`. While the job is paused it records what the module reports final (the items that were in flight finish and are reported once, settled and charged as any item), submits NOTHING, raises no `stale` event and never expires the job; if every item the module holds is final the job completes the normal way. A reserve and a slot are held for as long as the job is paused: **there is no automatic expiry of a pause**, the credits come back when the user resumes or cancels.
  - **A job `running` whose module report says `paused`** (the user resumed, or the engine died between the move and the call): the engine calls `POST /v1/resume` (idempotent) and goes on submitting the rest of the list.
  - **A job `cancelling`** (the user cancelled a running or paused-while-running job): the engine calls the module's cancel at every look until the module reports complete (module 1 `POST /v1/jobs/{id}/cancel` with the user's own key; modules 2 and 3 `POST /v1/cancel`, which also ends a hold), records every final item (module 1's unclaimed rows arrive as `cancelled` results, free, charge rule `M1-24`; the rows the engine never handed over get the platform's own `cancelled` result), then completes and finishes the job `cancelled` and releases the remainder of the reserve once.
  - **What the platform trusts.** Only the module's own report says whether it holds a campaign (`paused` in the campaign report of modules 2 and 3: the stored per-campaign pause, never the operator's `dispatch_paused`), and only the `paused` answer and the capability flag are read: module 2's `describe.capabilities.campaign_pause_resume` and module 3's `describe.capabilities.pause_resume`. A module whose describe lacks its flag is a module older than the routes: the engine sends nothing to it, writes one `flag` job event per staleness interval (kind `flag`, the operation and the module only) and the job stays paused here while the module may still be sending: an administrator decides. A run of an item the platform marked `cancelled` is refused by modules 2 and 3 with `409 job_item_cancelled` (a code of its own, not a conflict): the wrapper treats it as a refusal for good, never a wait.
  - **The lag, and the notes.** The API's answer is immediate (the job is `paused` when it is sent) and the module is told at the engine's next look; the engine writes a `note` job event whose reason begins `module_paused` when the module's report first says it holds the campaign and `module_resumed` when it stops saying so, once per change (the database drops a repeat, so a restart writes nothing twice). The difference between the transition event and the note is the lag.
  - **Not checked here:** this against the real modules (the live tests, after the modules are pinned and their recordings replace the hand-written bodies of the unit tests).
- **The switch.** `PLATFORM_JOB_ENGINE_ENABLED=false` starts no engine in that instance; the start-up log says `job engine is switched off` once. It is for an instance that must serve the API and the loops and not move jobs (and for the harness's legacy platform containers, whose tests write jobs by hand).
- **Not checked here:** the engine against the real modules and a real Postgres is the harness's (the crash stage kills the process at named points of a job's life; those points exist only in the harness image, which is built with a build tag the production image never has). A stand-in module in a unit test is not the module.

## What a module can do with an item that was never submitted

A `public.job_items` row that the module was never given (its job expired, was cancelled before it started or failed: marked `cancelled` in the transaction that ended the job, see "Running the job engine"; nothing is deleted) can turn into work through ONE path, read from the module code at the commits the harness builds (module 2 `d023fdb`, module 3 `59b2d2e`; `db/module-statements.txt` is the list of every statement of either module on the table and `scripts/check-module-reads.sh` fails when the code and the list differ), and **that path refuses a marked item**:

1. **The run route**, `POST /v1/run` with a `job_item_id` and a `user_id`. It reads `SELECT campaign_id, status IS NOT DISTINCT FROM 'cancelled' FROM public.job_items WHERE id = $1 AND user_id = $2` (statement J1) and copies the row into the module's OWN jobs table with `INSERT ... SELECT ... FROM public.job_items ji WHERE ji.id = $1 AND ji.user_id = $2 AND ji.status IS DISTINCT FROM 'cancelled'` (statement J2): the status test is in the SAME statements, so the refusal is atomic with the creation of the module's job. An item marked `cancelled` is refused **409 `job_item_cancelled`** (a code of its own, not a cause of `conflict`: the platform adapter maps it to `sendapi.ErrItemCancelled`, a refusal that can never succeed and is never taken for back-pressure), another tenant's item stays the plain 404, any other status and a NULL one run exactly as before, and the replay of a run that already created its job stays the idempotent replay (module 2 `store.go` lines 31-38 and 114-171, module 3 `store.go` lines 126-205; ADR-0018 of module 2 and ADR-0022 of module 3).
2. **Nothing else reads the table.** The claim, the retry, the requeue and the reclaim of both modules run over the module's own jobs table (`FOR UPDATE SKIP LOCKED` on `send_managed.jobs` and on `send_byo.jobs`): after the copy of path 1 a module never looks at `public.job_items` again. Module 3's test-send is the one other statement and it only INSERTS a new row with status `pending`. The remaining mentions are the foreign key of the module's jobs table, the preflight check (which now also requires the `status` column), the grants and comments.

So **no module acts on such an item**: no scanner finds it, no timer retries it, no requeue reaches it, and a direct run of it is refused. The guard has one honest limit: a marker committed after the run statement's snapshot but before the module commits cannot be closed from the module (it cannot lock the platform's row: its role has no UPDATE); the platform marks only the items of a job that has ENDED, and the engine submits only the rows of confirmed, scheduled, running and paused jobs, so the two never race. This is measured, not assumed: `tests/harness/jobs_live_items_test.go` expires a real module 3 job, shows its items marked and nothing of them at module 3 or at the sink, runs one marked item directly through the adapter and sees `ErrItemCancelled` and an unchanged sink, with the control job of the same user running and sending with its items unmarked; each module's own real-infrastructure suite 15 does the same at the module's API; `tests/harness/jobs_engine_schedule_test.go` pins the statements the modules issue, so that it is red on the day a module adds a statement on the table that does not refuse a marked item. The platform adds no trigger, policy or row-level security to `public.job_items` (`tests/harness/constraints_test.go` pins that nothing the platform does turns the table into a lock for the modules' own roles).

## Not checked

CI does not run GoTrue (no login is ever performed), the pooler (Supavisor), PostgREST or a hosted project's own grants and extensions, so step 1 and step 5 are verified by the owner, not by a runner; the `supabase` workflow measures migrations only, statement by statement, and the `harness` workflow measures the running stack on the same image. The leader election is exercised by two platform instances and by killing one, not under a network partition and not behind a transaction-mode pooler. Step 3b is exercised on the pinned image as `postgres`, not on a hosted project whose `postgres` role, role memberships (who created `verify_admin`) or default privileges differ: if `verify_admin` was created by another identity than the one running the file, the file stops at its membership grant with a message that says so.
