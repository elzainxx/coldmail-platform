WORKER (M3 docker-compose.yml:104-130): env CONTROL_HOST (the control's service name here: m3), CONTROL_WORKERLINK_PORT=8443, CONTROL_STREAM_PORT=8444, CONTROL_SERVER_NAME=control (the control cert SAN is DNS:control,DNS:localhost,IP:127.0.0.1, gen-certs.sh:80; the dial uses host and servername separately so host m3 with servername control verifies, stream.js:36-44), WORKER_ID=<uuid>, WORKER_TOKEN=<plaintext>, WORKER_HEARTBEAT_INTERVAL_SEC=10, WORKER_SMTP_TIMEOUT_MS=30000, MTLS_CLIENT_CERT/KEY, MTLS_CA_CERT mounted from M3's secrets/dev/certs (worker.crt, worker.key, ca.crt; the platform harness already runs M3's gen-certs/gen-secrets/own-secrets: run.sh stage 2; own-secrets chowns worker.key to uid 10002). REGISTRATION: the token is the authority, the cert is transport (C/workerlink/stream.go:364-385): the worker must exist as a row BEFORE it starts or it exits on register-reject (no restart policy): INSERT INTO send_byo.boxes (id, user_id, token_hash, status) VALUES (<worker uuid>, '00000000-0000-0000-0000-000000000000', <bcrypt hash of the token>, 'active') (boxes.user_id has an FK to public.users: the system user exists since platform_0001). Liveness without sleeps: SELECT status='active' AND last_heartbeat_at > <database clock taken before the worker started> FROM send_byo.boxes WHERE id=<worker uuid>. A verify-on-add needs an idle connected worker: if none, the account is stored `failed` and unroutable.
THE SINK'S TRAPS: (a) the worker skips TLS validation only for hosts localhost, smtp-sink and private IPs (M3 services/worker/src/smtp.js:136-145, used at :182): the sink service MUST be named `smtp-sink` (or the account must use a private IP) or verify-on-add fails; (b) Mailpit accepts any credential, keeps what it received, cannot delay, reject or throttle (M3 itself records that a controllable sink DOES NOT EXIST, docker-compose.yml:184-188); (c) its API is HTTP :8025 inside the network: GET /api/v1/messages?limit=500 (default limit 50; fields messages_count, messages[] with To[{Name,Address}], Subject, Created; field names for v1.33.1 are INFERENCE: check them on the first run), DELETE /api/v1/messages to reset, /api/v1/info for readiness; search is fuzzy ('message 1' matches 'message 10'): group by exact address, never by substring search; counts are cumulative.
FROM-GATE: the dispatch predicate requires the account's from-alignment to be aligned (or an acknowledged unaligned_warned) (C/dispatch/eligibility.go:56-63); the cheapest pass is the config key from_gate_mode=off: UPDATE send_byo.config SET value='{"v":"off"}' WHERE key='from_gate_mode' (what M3's own harness does, phase3_send.sh:72), read fresh per create (C/platformapi/from_gate.go:53-57), so set it BEFORE creating the account. fromgate/evaluator.go:90-95 then returns allow/aligned with no DNS lookup. Do NOT use the admin override_from_gate (it writes unverified). Sending needs no DNS beyond Docker's: the worker connects straight to smtp_host.
API CALLS (Bearer tokens; Domain A = the platform service token covers quote/run/report/describe and /v1/send-byo/*; Domain B = the admin key covers /v1/admin/*; errors {"error":{"code","message","details"?,"request_id"}}):
 1. out of band (superuser SQL): INSERT INTO auth.users(id,email); INSERT INTO public.users(id, auth_user_id, email) with auth_user_id = id and a lower-cased trimmed email.
 2. optional per-user pacing: PUT /v1/admin/users/{U}/config (admin key) body {"concurrency_per_user":1,"send_delay_min_sec":2,"send_delay_max_sec":2} -> 200 (strict decode: unknown fields are 400; send_delay_* may be 0, the others must be > 0, adminapi/user_config_override.go:84-105).
 3. POST /v1/send-byo/accounts (service token) body {"user_id":U,"smtp_host":"smtp-sink","smtp_port":1025,"smtp_username":"sender@example.test","smtp_secret":"anything","from_address":"sender@example.test","from_name":"Harness"}; smtp_port defaults to 587 if omitted so ALWAYS pass 1025 (port 465 = implicit TLS, anything else STARTTLS, dispatch.go:601-606); 201 body: {id,user_id,smtp_host,smtp_port,smtp_username,from_address,from_name,has_credential,status{paused,pause_reason,quarantined,disabled},verification{state,verified_at,verify_at},from_alignment{state,...},daily_limit,...}; ASSERT verification.state=="verified" AND from_alignment.state=="aligned" before sending (an unverified or unaligned account never sends and never errors); a duplicate (user,host,username) is 409, cap 20 accounts per user. Re-verify: POST /v1/send-byo/accounts/{id}/test?user_id=U (rate limit 5/day).
 4. rows in public.job_items (no API): INSERT INTO public.job_items(campaign_id,user_id,recipient_email,rendered_subject,rendered_body) SELECT $C,$U,'r'||g||'@example.test','[tag] '||g,'<p>m'||g||'</p>' FROM generate_series(1,$N) g RETURNING id. All items of one user's campaign share campaign_id (no FK); a second campaign of the same user with non-terminal jobs is 409 user_campaign_active. Use DISTINCT recipients (exactly-once assertions depend on it).
 5. POST /v1/run (service token) {"job_item_id":ID,"user_id":U} per item -> 202 {"job_id","state":"queued"}, repeat 200; 409 conflict when the user is SUSPENDED (the body does not say which conflict), another campaign is active or a cap is hit; 503 paused at dispatch rung refuse_new|stopped. Accept ALL items BEFORE suspending (a suspended user's /v1/run is refused).
 6. GET /v1/report?campaign_id=C&user_id=U&page_size=200 -> {"campaign_id","dispatch_paused","totals":{total,sent,bounced,failed,in_flight,pending,waiting_for_capacity},"progress":{terminal,fraction_complete,is_complete},"items":{"results":[{job_item_id,state,provider_message_id,attempt_count,account_id,...}],"next_cursor","page_size"}} (in_flight = assigned+sending; dispatch_paused reflects ONLY the global rung: per-user suspension is NOT visible in the report, observe it through `pending` not moving).
 7. suspend/unsuspend: POST /v1/admin/users/{U}/suspend|unsuspend (admin key) as in m3-suspend.txt.
PACING (C/dispatch/pacing.go:1-25, 86-131, 148-162): per-user LANES in memory: lanes = ceiling - in_flight; a lane admits when its timer has elapsed; a fresh lane is ready at once; each push stamps next_send_at = now + uniform[min,max] seconds; tick interval dispatch_tick_interval_ms=1000 and /v1/run kicks the dispatcher; defaults send_delay_min/max 3/7 s, concurrency_per_user 3. THE RECIPE for a deterministic mid-run halt: per-user override concurrency_per_user=1 and send_delay_min=max=2 -> about one send per 2-3 s, so 24 items take 50-70 s and a suspend after k=5 lands mid-run; ONE worker handles one job in flight (workerlink/stream.go:329-339): with concurrency_per_user>1 the extra claimed jobs are requeued with no_worker_available (lossless but churns job_events); keep one lane. Sends to Mailpit take <100 ms, so never try to catch a job mid-SMTP by polling. Do not restart m3 mid-test (the pacer is in memory). Sink recipients carry the per-recipient key (To[0].Address; the worker does RCPT TO:<recipient>).
HALT PROOF (M3's own tests, M3 C/dispatch/suspend_test.go:56-91, suspend_race_test.go:34-122, Docs/install-and-deploy.md:1952-1957): they drive Dispatcher.Tick() in-process with a recording pusher: no live test of the suspend route against a real worker existed. Observable facts to assert live: (1) after the suspend call returns, the number of job_events rows with from_state='queued' AND to_state='assigned' for that user's jobs and created_at > (SELECT suspended_at FROM send_byo.user_suspensions WHERE user_id=U) is ZERO (use the database clock only); (2) WAIT for in_flight==0 (bounded), THEN take the sink count S: with one lane at most ONE job can still complete after the call (an already-claimed job finishes: suspend_race_test T13b) so k <= S <= k + concurrency_per_user, S == totals.sent == count(send_logs); (3) hold a few ticks: the user's sink count is unchanged; the CONTROL tenant (never suspended, own account and campaign) keeps sending meanwhile, which proves the halt is the suspension and not a stalled stack; (4) after unsuspend (no dispatcher kick: latency up to one tick) the SAME job ids go queued -> sent, the sink ends with exactly N distinct recipients each once, no duplicates; assert exactly-once from the sink multiset against report items in state sent.
RISKS: nothing needs a published port (tests run inside the network); no external network; no privileged mode; do NOT mount docker.sock; sink.key stays owned by the host user (Mailpit reads it as root: fine on a normal runner); the `--wait` of compose returns 0 even with a dead worker (no healthcheck): wait on the DB heartbeat; one campaign per user at a time; the harness NOT CHECKED text in run.sh must stop saying workers and the sink are not started.
