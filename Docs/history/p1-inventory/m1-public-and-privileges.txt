## 0. The findings that matter most

1. **MISSING GRANT, and it is at startup: `policies` INSERT + UPDATE.** `M:129` calls `pg.EnsurePolicy` (`PG:417-440`), which runs
   `INSERT INTO policies … ON CONFLICT DO NOTHING` (`PG:419-422`) and `UPDATE policies SET is_default=true …` (`PG:431-434`).
   `cp_runtime` holds only `SELECT ON policies` (`0005:90`; no later migration widens it). A non-owner login holding today's
   grants gets 42501 here, before serving. A pre-seeded row does not help: **[PG]** the INSERT privilege is checked before the
   conflict is evaluated. Consequence (`M:129-133`): `buildAPI` returns early, so `/v1/verify` is 503, `/readyz` is not_ready
   (`WithPinger` is attached later, `M:182`), the bulk endpoint, the drainer and the health-watcher are never wired. The partition
   loop (started earlier, `M:122`) still runs. `EnsurePolicy` has **zero test callers** (grep) and is not in the `Store` interface, so
   nothing catches it. It is the only table-grant gap in the whole code base (section B).
2. **Migration `0014` hard-codes `public` and cannot be applied into `verify` unchanged.** `0014:35,79` (`SET search_path = pg_catalog, public`),
   `:55` (`to_regclass(format('public.%I', …))`), `:57` (`CREATE TABLE public.%I PARTITION OF public.verification_raw`), `:60-62`
   (`GRANT/COMMENT … public.%I`), `:81` (`SELECT public.ensure_verification_raw_partitions_at(…)`). On a `verify`-resident table
   both functions fail (42P01 / 42883) every call, **and the bootstrap call at `0014:94` aborts a fresh install** (`psql
   ON_ERROR_STOP` in `ci:60`, `t.Fatalf` in `internal/testpg/testpg.go:123`). It is the only migration with a literal `public`
   (14 of 15 are schema-agnostic and land in the first schema of the applying session's `search_path`). A 0016 that moves a
   0015-state database must `CREATE OR REPLACE` both function bodies (function bodies are text; moving the function does not
   rewrite them).
3. **Every Go statement is unqualified** (all of `PG`, `PF`, `PT:34`). With the login's default `"$user", public` and tables in
   `verify`, every query is 42P01. Nothing in non-test Go sets or reads `search_path`/role; the pool is `pgxpool.New(ctx, dsn)`
   (`PG:50`). pgx 5.10.0 turns an unknown DSN key into a startup runtime parameter
   (`pgx/v5@v5.10.0/pgconn/config.go:50,434-437`), so `TM_DATABASE_URL=…?search_path=verify` works with no code change (not
   tested here). `PG:135` lists `search_path` as non-secret for DSN redaction only.
4. **The tests are all superuser; only 2 files ever drop to `cp_runtime`, and via `SET LOCAL ROLE`.** `TM_TEST_DATABASE_URL` is
   `postgres://postgres:ci@…` (`ci:67,83`) and serves as both the store DSN and the seeding/cleanup DSN. Seeding as the store's own
   pool needs owner rights (`INSERT INTO api_callers`: `internal/api/pg_tenancy_test.go:104,328`, `postgres_test.go:622`; `DELETE FROM
   verifications/jobs/work_items`: `pg_tenancy_test.go:174-177`, `pg_e2e_test.go:109-112`). A `verify_app` DSN cannot be the shared test
   DSN. The SECURITY DEFINER wrapper is owned by `postgres` (superuser) in CI, so the owner-side requirements in finding 5 are never exercised.
5. **`cp_admin` owns nothing and cannot do the DDL the docs say it does.** Every object is owned by whoever ran the migration
   (`postgres` in CI, `Docs/install-and-deploy.md:38`, `testpg.go:101-123`). `cp_admin` only holds `GRANT ALL PRIVILEGES` on tables
   (= DML + TRUNCATE/REFERENCES/TRIGGER; **[PG]** not ALTER/DROP/partition DDL, which need ownership) and no schema grants. The
   runbook step "as `cp_admin` run `SELECT ensure_verification_raw_partitions_at(now(), 3)`" (`Docs/operator-runbook.md:226`)
   would need ownership of `verification_raw` + CREATE on the schema (**[PG]** the creator of a partition must own the parent). Same
   for `verify_owner`-owned SECURITY DEFINER: it must own `verification_raw` and have CREATE on `verify`.
   No `GRANT USAGE ON SCHEMA`, no sequence grants, no `ALTER DEFAULT PRIVILEGES` exist anywhere: today's table access rides on the
   implicit PUBLIC USAGE of schema `public`; `verify` needs explicit USAGE grants.
6. M1 reads neither `public.users` nor `public.job_items` (section E).

### A.0 How they are created
No migration contains `CREATE SCHEMA`, `SET search_path`, `OWNER TO`, `SET ROLE`, or a schema-qualified name except `0014`. Owner of every
object = the session user that applied the file: `postgres` (superuser) in CI (`ci:60`), in `testpg.Scratch` (`testpg.go:101,123`, simple-protocol

migration tracking table (`migrations/README.md:142`); every `CREATE` is `IF NOT EXISTS`, so a same-named table already present in the target
schema is silently skipped, not an error (generic names: `cache`, `jobs`, `nodes`, `policies`, `calibration`).

  (it never UPDATEs `verifications`, `verification_raw`, `send_outcomes`, `api_callers`, `external_calls`, `node_audits`, `work_item_attempts`).
  If column-level UPDATE is ever used, **[PG]** `SELECT … FOR UPDATE` (`PG:617`, `PG:805-808`) needs UPDATE on at least one column of that table.
- **Sequences:** no INSERT depends on a serial/identity (A.3). No sequence USAGE is needed. All ids are app-generated UUIDv7 (`idgen`).
- **INSERT … RETURNING / ON CONFLICT DO UPDATE** (`PG:770` `RETURNING id`, `PG:556`, the 6 upserts) also need S on the returned/arbiter columns; all those tables hold S.
- **FK checks** (`verification_raw → verifications`) **[PG]** run as the referenced table's owner, so the runtime needs no S/REFERENCES for them.

### B.3 What fails for a non-owner, non-superuser login that holds only today's `cp_runtime` grants
1. `EnsurePolicy` (startup): 42501 on `policies` INSERT (`PG:420`), see finding 1. Everything downstream of `M:133` is never wired.
2. Every other statement in B.2 is covered table-by-table (verified above); the DEFINER wrapper runs as its owner (`postgres` today).
3. Not a grant but a precondition today's migrations never create: `cp_runtime` is `NOLOGIN` and no membership/`LOGIN` exists, so a login role
   needs `GRANT cp_runtime TO <login>` (or `ALTER ROLE … LOGIN`); neither is in any migration. Schema USAGE comes only from PUBLIC (A.5).
4. In a schema other than `public`, additionally: schema USAGE, and the DEFINER function's owner must own `verification_raw` and have CREATE on the schema (finding 5).

## D. How the database is configured; what 0016 touches

### D.1 DSN and pool
- Runtime DSN: env **`TM_DATABASE_URL`** (`config.go:587-588`) → `Config.DatabaseURL` (`config.go:284`) → `M:101,109` → `store.OpenPG` (`PG:49-59`):
  `pgxpool.New(ctx, dsn)` (`PG:50`) then `pool.Ping` (`PG:54`). Default pool config: no `AfterConnect`/`BeforeAcquire`/`RuntimeParams` edits, no `SET ROLE`,
  no `SET search_path` anywhere in non-test Go. Empty DSN → `/v1/verify` 503 (`M:101-105`). `TM_SUPABASE_KEY` has no consumer (`Docs/install-and-deploy.md:148`).
- Errors from pgx are scrubbed so the DSN never reaches a log (`PG:81-107`, `scripts/check-no-secret-leak.sh`).
- A role- or schema-selecting DSN needs no Go change: pgx v5.10.0 passes any non-recognised DSN key as a startup runtime parameter (`pgconn/config.go:50,434-437`; `PGOPTIONS` → `options`
  `:602`). Behind a transaction pooler startup parameters may be rejected (**[PG]/infra, not verifiable from this repo**); `ALTER ROLE verify_app SET search_path = verify` avoids that.
- Test DSN: env **`TM_TEST_DATABASE_URL`** (superuser), read with `os.Getenv` in `testpg.go:37`, `postgres_test.go:26`, `pg_tenancy_test.go:78`, `readyz_test.go:439`, `pg_e2e_test.go:22`;
  `testpg.Scratch` derives `cm_scratch_<hex>` databases from it via `CREATE DATABASE` (`testpg.go:73-96`). `/readyz` only pings (`api.go:632`).
