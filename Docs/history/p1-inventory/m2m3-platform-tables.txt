### 3. Constraints / indexes relied on
- A PRIMARY KEY or UNIQUE constraint on `users(id)` is mandatory (all FKs above; `ON CONFLICT (id)` in test seeders). The preflight does NOT check this (it checks existence only, `check_platform_tables.sql:3-4`).
- All FKs: not DEFERRABLE, no `ON UPDATE` clause (= NO ACTION). Actions: `RESTRICT` (pools.user_id), `CASCADE` for every other FK (list U5-U10).
- Effect on platform `DELETE FROM public.users`: cascades through `pools.owner_user_id, accounts, boxes, job_events, send_logs, account_events`; BLOCKED while any `send_managed.pools.user_id` row references it. A dedicated pool has `user_id = owner_user_id` (`pool_handlers.go:102-103`: `userID = *req.OwnerUserID`), so deleting a dedicated-pool owner is refused by `pools_user_fk RESTRICT` until the pool is deleted; the all-zero system user can never be deleted while a shared pool exists (shared pools have `user_id = SystemUserID`, `pool_handlers.go:79`). (RESTRICT-vs-cascade ordering is my reading of Postgres semantics, not exercised by an M2 test.)
- Index needs on the platform side: only the PK. Module-side referencing columns are all indexed (`0011:52,60-65,75`, `0008:82`, `0009:45`, `0014:49-50`), so cascades from a users delete need nothing more.
- **Required ROW**: id `00000000-0000-0000-0000-000000000000` must exist in `public.users`. M2 cannot create it (SELECT-only); shared-pool/shared-account creation returns 409 `system_user_not_provisioned` until it exists (`pool_handlers.go:70-77`, `account_create.go:88-95`, `account_update.go:139-146`). The same row is the `user_id` of every shared pool/account (`pools_user_fk`, `accounts_user_fk`).

### 2. Columns used

| column | R/W | role | Go type | SQL type/nullability the code REQUIRES |
|---|---|---|---|---|
| `id` | R (J1/J2 filters; J4 `RETURNING id`) and **default-generated on INSERT (J4 omits it)** | runtime | scanned into `string` | **uuid PK with a DEFAULT (gen_random_uuid())**. Without a default J4 fails with 23502. |

| `status` | **W only** (J4 literal `'pending'`); never read | runtime | literal | must exist, must ACCEPT `'pending'` (no CHECK/enum that excludes it); nullable or defaulted not required since J4 always supplies it |
| `created_at` | never used by code | - | - | any default; J4 omits it, so if the platform has it, it must be nullable or defaulted |

### 3. Constraints and indexes
- PK/unique on `job_items(id)` (FK J5; test-only `ON CONFLICT (id)`).
- No platform FK on `campaign_id` (see above). A `job_items.user_id` -> users FK is optional for the module and harmless for J4: the tenant's user row exists because J4 only runs after `accountConsumeSpecific(ctx, userID, accountID, ...)` found an account owned by that user (`dispatch/eligibility.go:387-392`, `send_test_action.go:52`), and `accounts_user_fk` requires the user row.

- Indexes: PK covers `id = $1 AND user_id = $2`.
- `jobs.campaign_id` has NO FK to `send_byo.campaigns` (deferred, FW-M3-20; `store.go:38-41`, `0032:15-23`), so a campaign_id that has no campaigns row (the test-send case) is accepted.

## Tenant id

- **Type: `uuid` everywhere.** Every tenant/user id column in the modules is `UUID` (`user_id UUID NOT NULL` in pools/accounts/boxes/jobs/job_events/send_logs/account_events; `owner_user_id UUID`; M3 `user_settings.user_id`, `user_config_overrides.user_id`, `user_suspensions.user_id`, `campaigns.user_id`, `notifications.user_id`). FKs from these to `public.users(id)` force `users.id` to be uuid.
- Go side: carried as plain `string` (never `uuid.UUID`/`pgtype.UUID`; no `google/uuid` import). Scanned from uuid columns into `string` (pgx v5). Validated at the API edge by the regex `^[0-9a-fA-F]{8}-...-[0-9a-fA-F]{12}$` (canonical hyphenated form only: M2 `platformapi/handlers.go:45,134,149,223,236,241`, `adminapi/helpers.go:58-61`; M3 `platformapi/handlers.go:48,91,137,152,226`, `adminapi/helpers.go:61-64`). So a tenant id that is not a canonical hyphenated UUID is rejected 4xx before SQL.
- Parsing/casting/compare as another type: (a) `isUUID`/`uuidToBytes` (`adminapi/uuid.go:25`, `platformapi/uuid.go:23` (M3 line numbers), `dispatch/dispatch.go` `parseUUID` at M2 `:629`, M3 `:631`) parse only the **account** id into 16 bytes for AES-GCM AAD, not the tenant id. (b) `pg_advisory_xact_lock(hashtext('send_*.campaign_start:' || $1::text))` casts the tenant id to **text** (M2 `store.go:53`, M3 `store.go:63`, M3 `platformapi/account_create.go:168` `'send_byo.account_create:' || $1::text`). (c) `qu.user_id::text`, `account_id::text` in read-outs (`M3 adminapi/health_store.go:437`). (d) `$8::uuid` casts for `updated_by` (M3 `adminapi/user_config_override.go:256,264,292`). (e) Lexicographic compare/sort of tenant ids as strings for the fairness ring (`M2 dispatch/loop.go:140,226`, `M3 dispatch/loop.go:183,273`: `sort.Slice(... userID < ...)`, `slot.userID > cursor`) - this uses the canonical lower-case text form pgx returns; do not return upper-case/other forms.
- Special values: M2 requires the all-zero uuid as a real `users` row (system user). M3 never needs it in code. M3 uses a non-user sentinel `00000000-0000-0000-0000-00000000adf1` only as an un-FK'd `updated_by`.
- Test-send (M3): `job_items.campaign_id := user_id` (both the tenant uuid), `send_test_action.go:96-99`.

### Decisions I had to make (where the code is silent or two readings exist)

1. `users.id` / `job_items.id` = **uuid** (forced by the module `UUID` FK columns; text would not create the FKs).
2. PRIMARY KEY on `id` for both tables (FK target + `ON CONFLICT (id)`); no composite or surrogate alternative considered.
3. `DEFAULT gen_random_uuid()` on **both** ids (M3 prod INSERT omits `job_items.id`; tests omit `users.id`); not `GENERATED ALWAYS` (tests insert explicit ids: `runner_integration_test.go:986`, `ON CONFLICT (id)` seeders).
4. `job_items.campaign_id` and `user_id` both `uuid NOT NULL` (non-pointer Go `string` scans + `jobs` NOT NULL columns); `campaign_id` has **no FK and no check** (M3 test-send writes the user's id there).
5. `recipient_email`, `rendered_subject`, `rendered_body` `NOT NULL`; `reply_to` nullable. Chosen over keeping them nullable (as the fixture does) because a NULL becomes an opaque 500 `create_job_failed`, not a clean 4xx (C1).
6. `status` = `text NOT NULL DEFAULT 'pending'` with no CHECK. The only value any module writes is `'pending'`; nobody reads it, so the full vocabulary is the platform's to define but must include `'pending'`. NOT NULL/default is my choice; the code only needs the column to exist and accept `'pending'`.
7. `created_at` on job_items is kept (fixture parity) but defaulted, since M3's INSERT omits it; any other future platform column on job_items must be nullable or defaulted for the same reason.
8. `email`, `is_active`, `created_at` kept on `users` although NO non-test code reads them, solely because the module test factories/seeders insert/order on them; if the platform drops them the module suites that point at the real table would break (module suites currently build their own fixture, so this is a compatibility choice, not a code requirement).
