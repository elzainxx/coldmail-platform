WHY M1'S RULES ARE DELIBERATELY NOT M2/M3'S. Those repos enumerate each Go package
by name on a `go_suite` line, so a new package is invisible until someone edits the
list — that is the exposure their gate closes. M1 does not have it: CI runs
`go test -v ./...` over a single module, and RSpec uses its default
`spec/**/*_spec.rb` glob with no pattern/exclude/default_path override anywhere
(.rspec carries only --require and --format). Both discover new tests
automatically. Porting M2/M3's rule 1 here would have produced a gate that can
never fail — the exact vacuity this project keeps hitting, and the reason a
sweep of M1 for unwired packages came back clean rather than "not applicable."

So this gate guards the DISCOVERY PROPERTIES THEMSELVES — the five ways M1 can
silently lose automatic discovery:

  1. CI still runs `go test ./...` and not a hand-listed subset. If that changes,
     M1 ACQUIRES M2/M3's exposure and the gate says to port their rule, not to
     delete this one.
  2. Exactly ONE go.mod. `go test ./...` walks only the module it runs in, so a
     second module's tests vanish from a green run with no error and no skip.
  3. No _test.go behind a build constraint. A //go:build tag removes a file from
     `go test ./...` while it still compiles and vets clean under that tag — the
     same "green signal, zero coverage" shape as an unwired package, and the only
     way to defeat rule 1's automatic discovery without touching CI. BOTH syntaxes
     are checked; Go still honours the legacy `// +build`, so knowing only the
     modern form would make the rule bypassable in one line.
  4. RSpec discovery is not narrowed — neither .rspec (--pattern,
     --exclude-pattern, --default-path) nor spec_helper.rb (config.pattern).
     Either drops spec files while the suite still reports green.
  5. Every scripts/check-*.sh is named in ci.yml. The one rule that transfers
     verbatim, and the one whose failure mode is already on this project's record.

gen-config-reference.sh is deliberately OUT of rule 5's scope: it is the
GENERATOR, and it is exercised in CI through check-config-reference-fresh.sh, which
IS enumerated. The glob is check-*.sh precisely so a generator cannot be mistaken
for a gate; selftest case 10 pins that so a later "tidy this to scripts/*.sh"
cannot land quietly.

A REAL DEFECT, FOUND BY BREAK-VERIFYING RATHER THAN BY REASONING. Rule 1's first
version grepped for `go test ./...` anywhere in the workflow. ci.yml's own comment
explaining this gate contains that string. So the break — replace the real command
with a hand-listed package subset — left the gate GREEN: it was satisfied by prose
ABOUT itself, the purest form of the vacuity it exists to prevent. Rule 5 had the
`run:` anchor from the start; rule 1 did not, and only running the break on the real
tree showed the difference. Fixed by anchoring to a `run:` line, with selftest case
11 reproducing the exact shape (hand-listed command PLUS a comment mentioning the
glob) so the anchor cannot be dropped again.
