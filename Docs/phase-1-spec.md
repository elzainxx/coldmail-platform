## How faults are proven in this phase (replaces one branch per gate)

No `fault/*` branches. Each fault is a patch, `ci/faults/p1/<gate>.patch`, beside `ci/faults/p1/<gate>.expect` naming the **command**, the **step** it must fail at and the **message** it must print. The `fault-proofs` workflow (`workflow_dispatch`) runs one matrix leg per `.expect`; a leg first runs the command on the **unpatched** checkout (it must pass — the paired control), then applies the patch to a scratch copy and requires a **non-zero exit at the named step with the named message**. A red for the wrong reason fails the leg. A leg that cannot apply its patch fails (and an always-on gate, `check-fault-patches`, fails the push when a patch stops applying — a dispatch-only proof must not rot unseen). Only gates **new or changed in Phase 1** are proven here; the sixteen Phase 0 gates were proven in Phase 0 and their fault diffs are archived (not re-run) under `ci/faults/p0/`. A fault that needs a token-shaped string is **generated by its leg**, never stored (a stored token trips gitleaks).

## Design choices (mine — overturn any and I rework only that chunk)

- **M1 schema addressing follows M2/M3:** every SQL statement names `verify.<table>`; no reliance on `search_path`. (M2/M3 write `send_managed.config` etc.; none sets `search_path`.)
- **M1 roles:** `verify_owner` (NOLOGIN, owns every object), `verify_app` (LOGIN, runtime, password set out of band), `verify_admin` (NOLOGIN, break-glass). Forward migration `0016` only; M1's tooling is a `psql` loop with no history table, so there is nothing to rewrite.
- **The public-schema gate is an allowlist**, not a list of M1 names: after every chain has run, `public` may hold only what `tests/public-allowlist.txt` names (the platform's `users`, `job_items` and their own indexes/sequences). Any other table, sequence, type, function or view fails — so it also catches a *module 2/3* leak and a future platform leak.
- **Faults live in `ci/faults/p1/`**, each leg needing only a service Postgres (`postgres:16-alpine@sha256:aa6cb33c…`, the digest the harness already pins) — no Docker Compose, no module images — except legs whose subject is module source (they fetch that one module at its pin).
- **Supabase job:** `supabase/postgres` pinned by digest; migrations applied **one file at a time as `postgres`** (non-superuser there); every failure is recorded with file, statement and SQLSTATE; the job passes iff the failures equal `tests/supabase/known-blockers.txt` exactly (a new blocker, or a listed one that stopped failing, is red). The main harness moves onto this image only if the blocker list is empty.

## Locked here (Phase 1 — the one-way doors)

Written before the tables exist; each is enforced by the database or by a named gate, never by convention.

1. **Credits are integers.** `bigint` for every balance, delta and amount; unit costs are `integer`. No `numeric`, `real`, `double precision` or `money` column anywhere in schema `platform` (a catalog test fails on one). A unit cost is ≥ 1; the vendor-fallback cost is an integer > 1 set by an admin (seeded 2 — open decision 3).
2. **IDs.** Entity ids are `uuid` (`gen_random_uuid()`, v4, core in PG 13+). Append-only logs (`ledger`, `admin_audit`, `unit_cost_history`) use `bigint GENERATED ALWAYS AS IDENTITY` — strictly ordered, cheap to index, referenceable. The tenant is a person: `public.users.id uuid` = Supabase `auth.users.id`.
3. **Time.** Every instant is `timestamptz`, stored UTC; the `platform_app` session timezone is `UTC` (role setting). No `timestamp without time zone` column in `platform` (catalog test).
4. **Email normalisation for suppressions = module 1's frozen `norm/v1`** (`control-plane/internal/hash`): trim; exactly one `@`; domain — strip one trailing dot, IDNA ToASCII (punycode, lower-case), NFC; local part — NFC and lower-case; **no dot-stripping, no `+tag` folding**. The Go side produces it (P5/P6); the database enforces what SQL can: trimmed, one `@`, non-empty both sides, all lower-case, `IS NFC NORMALIZED`, domain only `[a-z0-9.-]` with no trailing dot, ≤ 254 bytes. One rule across verify and suppress, so a suppressed address and a verified address are the same address.
5. **Balance invariant — enforced by the database, and recomputed by a gate.** `platform.balances` holds `available` and `reserved`; **no role can write it** (`platform_app`/`platform_admin` hold SELECT only). Its only writer is an `AFTER INSERT` trigger on `platform.ledger` (a `SECURITY DEFINER` function owned by `platform_owner`) that upserts the balance row with the row's `available_delta` / `reserved_delta`, so the stored balance changes only in the same transaction as the ledger row that explains it. `CHECK (available >= 0 AND reserved >= 0)` makes overdraw a database error, not a code path. A view `platform.balance_drift` recomputes `SUM(delta)` per (user, module) and lists every row where stored ≠ recomputed (or where a ledger sum has no balance row); `scripts/check-balance-invariant.sh` fails on any row and is proven by a fault patch. *Why both:* the trigger makes drift impossible for every writer that passes through the ledger; the recompute gate is the only thing that notices if someone disabled the trigger or a migration broke it — a control and its paired alarm.
6. **The ledger is append-only for everyone but the table owner, and the owner is honest-reported.** `platform_app` and `platform_admin` hold SELECT and INSERT only (UPDATE/DELETE/TRUNCATE → SQLSTATE 42501). Defence in depth: row-level `BEFORE UPDATE OR DELETE` and statement-level `BEFORE TRUNCATE` triggers that raise (they also stop `platform_owner`). What the owner can still do — `ALTER TABLE … DISABLE TRIGGER`, drop the trigger, re-grant itself — is **demonstrated by a test, not hidden**; the compensating controls are that `platform_owner` is NOLOGIN, used only by the migrator, and that the balance-drift gate would show any tampering that changed a delta.
7. **Ledger row shape is enforced per kind by `CHECK`s** (grant / reserve / charge / release / m3_enable / m3_disable / m3_expire; sign pattern, required references, the arithmetic `units × unit_cost`). **The unit cost is frozen on the reserve row**; a charge row carries the unit and the frozen price and is tied to the job's frozen price snapshot by a composite foreign key, so settlement cannot use the current table (mechanism and the M1 problem it solves: design note below).
8. **Tenant id type: `uuid`** — module 1 (`owner_user_id uuid`), modules 2 and 3 (`public.users.id uuid`). *Confirmed against the inventory below; any module that disagrees is listed there, not decided here.*
9. **`platform.*` names, no `ALTER DEFAULT PRIVILEGES`** (Phase 0 rule): every table gets explicit grants in the migration that creates it, and the grants test fails on a table or privilege nobody declared — now **including column-level privileges and module-role privileges on `public.users`/`public.job_items`**.
10. **Nothing in `public` except the platform's own `users` and `job_items`.** Enforced by the allowlist gate on every chain.

*Design note — why a price snapshot table.* M1's price depends on the outcome (own 1, cache 1, vendor > 1), known only at settlement, but the credits must be reserved at confirm. One `unit_cost` on one reserve row cannot cover a mixed settlement. So: `jobs.frozen_settings` records the settings, `platform.job_unit_prices(job_id, unit, cost)` snapshots **every unit price of the job's module at confirm** (insert-only), the **reserve row freezes the reserve rate** (the dearest of them — what was held per unit), and each **charge row's `(job_id, unit, unit_cost)` must exist in the snapshot** (composite FK). P2 fills these; the shape that makes the locked rule ("settle at the frozen cost") a database fact is decided here, because it is not additive later.

## Open decisions (yours)

1. **M1's roles `cp_runtime` / `cp_admin`:** *(decided in A2.2 — see below)*.
2. **Scheduled jobs and "one active job per module per user".** Default here: the unique index covers `running`, `paused`, `cancelling` only; a `scheduled` job (credits reserved, not started) does **not** occupy the slot, and P4's start rule checks it. If you want a scheduled job to block a second one, the index changes (a migration, not a rewrite).
3. **Vendor-fallback price seed.** The plan says "admin-set, > 1". Seeded 2 so the table is complete; the CHECK is `> 1`. Pick the real number before launch.
4. **No clawback kind.** The locked kinds are grant / reserve / charge / release / m3_*; a mistaken grant has no kind that reverses it (a negative grant is refused by the sign check). Adding `adjust` is additive (a `CHECK` edit). P2 decides.
5. **`platform.admins` is added** (not in the plan's table list): "a named admin" has to be a row to be a foreign key. Admins are created out of band (migration/runbook), not by the app, until you say otherwise.
6. **Supabase Data API.** On a Supabase project, tables a migration creates in `public` are readable by `anon`/`authenticated` through the REST API unless revoked. B2 revokes them explicitly (and the Supabase job asserts it); whether to also enable RLS is yours.
