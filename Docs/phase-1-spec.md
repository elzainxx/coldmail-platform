## How faults are proven in this phase (replaces one branch per gate)

No `fault/*` branches. Each fault is a patch, `ci/faults/p1/<gate>.patch`, beside `ci/faults/p1/<gate>.expect` naming the **command**, the **step** it must fail at and the **message** it must print. The `fault-proofs` workflow (`workflow_dispatch`) runs one matrix leg per `.expect`; a leg first runs the command on the **unpatched** checkout (it must pass — the paired control), then applies the patch to a scratch copy and requires a **non-zero exit at the named step with the named message**. A red for the wrong reason fails the leg. A leg that cannot apply its patch fails (and an always-on gate, `check-fault-patches`, fails the push when a patch stops applying — a dispatch-only proof must not rot unseen). Only gates **new or changed in Phase 1** are proven here; the sixteen Phase 0 gates were proven in Phase 0 and their fault diffs are archived (not re-run) under `ci/faults-archive/p0/`. A fault that needs a token-shaped string is **generated by its leg**, never stored (a stored token trips gitleaks).

## Design choices (mine — overturn any and I rework only that chunk)

- **M1 schema addressing follows M2/M3:** every SQL statement names `verify.<table>`; no reliance on `search_path`. (M2/M3 write `send_managed.config` etc.; none sets `search_path`.)
- **M1 roles:** `verify_owner` (NOLOGIN, owns every object), `verify_app` (LOGIN, runtime, password set out of band), `verify_admin` (NOLOGIN, break-glass). Forward migration `0016` only; M1's tooling is a `psql` loop with no history table, so there is nothing to rewrite.
- **The public-schema gate is an allowlist**, not a list of M1 names: after every chain has run, `public` may hold only what `tests/public-allowlist.txt` names (the platform's `users`, `job_items` and their own indexes/sequences). Any other table, sequence, type, function or view fails — so it also catches a *module 2/3* leak and a future platform leak.
- **Faults live in `ci/faults/p1/`**, each leg needing only a service Postgres (`postgres:16-alpine@sha256:aa6cb33c…`, the digest the harness already pins) — no Docker Compose, no module images — except legs whose subject is module source (they fetch that one module at its pin).
- **Supabase job:** `supabase/postgres` pinned by digest; migrations applied **one file at a time as `postgres`** (non-superuser there); every failure is recorded with file, statement and SQLSTATE; the job passes iff the failures equal `tests/supabase/known-blockers.txt` exactly (a new blocker, or a listed one that stopped failing, is red). The main harness moves onto this image only if the blocker list is empty.

## Locked here (Phase 1 — the one-way doors)

Written before the tables exist; each is enforced by the database or by a named gate, never by convention.

1. **Credits are integers.** `bigint` for every balance, delta and amount; unit costs are `integer`. No `numeric`, `real`, `double precision` or `money` column anywhere in schema `platform` (a catalog test fails on one). A unit cost is ≥ 1; the vendor-fallback cost is an integer > 1 set by an admin (seeded 2 — open decision 3).
2. **IDs.** Entity ids are `uuid` (`gen_random_uuid()`, v4, core in PG 13+). Append-only logs (`ledger`, `admin_audit`, `unit_cost_history`) use `bigint GENERATED ALWAYS AS IDENTITY` — strictly ordered, cheap to index, referenceable. The tenant is a person: `public.users.id uuid` = Supabase `auth.users.id`.
3. **Time.** Every instant is `timestamptz`, stored UTC; the `platform_app` session timezone is `UTC` (role setting). No `timestamp without time zone` column in `platform` (catalog test).
4. **Email normalisation for suppressions = module 1's frozen `norm/v1`** (`control-plane/internal/hash`): trim; exactly one `@`; domain — strip one trailing dot, IDNA ToASCII (punycode, lower-case), NFC; local part — NFC and lower-case; **no dot-stripping, no `+tag` folding**. The Go side produces it (P5/P6); the database enforces what SQL can: trimmed, one `@`, non-empty both sides, all lower-case, `IS NFC NORMALIZED`, domain only `[a-z0-9.-]` with no trailing dot, ≤ 254 bytes. One rule across verify and suppress, so a suppressed address and a verified address are the same address.
5. **Balance invariant — enforced by the database, and recomputed by a gate.** `platform.balances` holds `available` and `reserved`; **no role can write it** (`platform_app`/`platform_admin` hold SELECT only). Its only writer is an `AFTER INSERT` trigger on `platform.ledger` (a `SECURITY DEFINER` function owned by `platform_owner`) that upserts the balance row with the row's `available_delta` / `reserved_delta`, so the stored balance changes only in the same transaction as the ledger row that explains it. `CHECK (available >= 0 AND reserved >= 0)` makes overdraw a database error, not a code path. A view `platform.balance_drift` recomputes `SUM(delta)` per (user, module) and lists every row where stored ≠ recomputed (or where a ledger sum has no balance row); `scripts/check-balance-invariant.sh` fails on any row and is proven by a fault patch. *Why both:* the trigger makes drift impossible for every writer that passes through the ledger; the recompute gate is the only thing that notices if someone disabled the trigger or a migration broke it — a control and its paired alarm.
6. **The ledger is append-only for everyone but the table owner, and the owner is honest-reported.** `platform_app` and `platform_admin` hold SELECT and INSERT only (UPDATE/DELETE/TRUNCATE → SQLSTATE 42501). Defence in depth: row-level `BEFORE UPDATE OR DELETE` and statement-level `BEFORE TRUNCATE` triggers that raise (they also stop `platform_owner`). What the owner can still do — `ALTER TABLE … DISABLE TRIGGER`, drop the trigger, re-grant itself — is **demonstrated by a test, not hidden**; the compensating controls are that `platform_owner` is NOLOGIN, used only by the migrator, and that the balance-drift gate would show any tampering that changed a delta.
7. **Ledger row shape is enforced per kind by `CHECK`s** (grant / reserve / charge / release / m3_enable / m3_disable / m3_expire; sign pattern, required references, the arithmetic `units × unit_cost`). **The unit cost is frozen on the reserve row**; a charge row carries the unit and the frozen price and is tied to the job's frozen price snapshot by a composite foreign key, so settlement cannot use the current table (mechanism and the M1 problem it solves: design note below).
8. **Tenant id type: `uuid`** — module 1 (`owner_user_id uuid`), modules 2 and 3 (`public.users.id uuid`). *Confirmed against the inventory below; any module that disagrees is listed there, not decided here.*
9. **`platform.*` names, no `ALTER DEFAULT PRIVILEGES`** (Phase 0 rule): every table gets explicit grants in the migration that creates it, and the grants test fails on a table or privilege nobody declared — now **including column-level privileges and module-role privileges on `public.users`/`public.job_items`**.
10. **Nothing in `public` except the platform's own `users` and `job_items`.** Enforced by the allowlist gate on every chain.

*Design note — why a price snapshot table.* M1's price depends on the outcome (own 1, cache 1, vendor > 1), known only at settlement, but the credits must be reserved at confirm. One `unit_cost` on one reserve row cannot cover a mixed settlement. So: `jobs.frozen_settings` records the settings, `platform.job_unit_prices(job_id, unit, cost)` snapshots **every unit price of the job's module at confirm** (insert-only), the **reserve row freezes the reserve rate** (the dearest of them — what was held per unit), and each **charge row's `(job_id, unit, unit_cost)` must exist in the snapshot** (composite FK). P2 fills these; the shape that makes the locked rule ("settle at the frozen cost") a database fact is decided here, because it is not additive later.

**Owner of each public object.** Module 1's are *module-owned*. The only *platform-owned (read by a module)* objects are `public.users` and `public.job_items`; no module creates them and the platform did not until B2. After Part A, `public` may hold only those two tables and what belongs to them (their own indexes) — enforced by the allowlist gate.

**Name clashes with the platform's planned objects.** The platform's planned tables are in schema `platform` except `public.users` and `public.job_items`. The one generic name shared across owners is **`jobs`**: M1 `public.jobs` (before the move), `send_managed.jobs`, `send_byo.jobs`, `platform.jobs` — four tables, four schemas, harmless once each is in its own schema and every statement qualifies its table, and a live hazard before that (an unqualified `jobs` resolves by `search_path`). No other planned platform name (`modules`, `admins`, `unit_costs`, `unit_cost_history`, `job_unit_prices`, `balances`, `ledger`, `m3_entitlements`, `suppressions`, `admin_audit`) matches a module table. No role name clashes (`platform_*`, `send_managed_*`, `send_byo_*`, `verify_*`). Advisory-lock keys: platform `7_xxx_xxx_xxx`, M3 `8_`, M2 `9_`; M1's `hashtext(…)` keys are 32-bit and cannot reach that band.

**M1 runtime privileges against its code.** Every runtime statement (startup, background loops, per request) was matched to what `cp_runtime` holds. **One gap, at startup:** `EnsurePolicy` runs `INSERT INTO policies … ON CONFLICT DO NOTHING` and `UPDATE policies SET is_default` before serving, and `cp_runtime` held only `SELECT` on `policies`; a login holding exactly the old grants fails there (42501) and M1 never serves (`/v1/verify` 503, `/readyz` not ready, the bulk endpoint, the drainer and the health watcher never start). `EnsurePolicy` had no test. Migration 0016 adds `INSERT` and column-level `UPDATE (is_default)`. Grants no code uses (kept, not pruned — pruning is a separate decision): `cache` DELETE, `verification_outcomes` (whole grant), `verification_raw` and `work_item_attempts` SELECT, the per-partition grants (inserts route through the parent), and everything `cp_admin` holds.

**Module 2/3 constraints on the platform's two tables** (from code; the shape itself is declared in B1): `users.id` and `job_items.id` are `uuid` primary keys (foreign-key targets) with defaults (M3's INSERT omits `job_items.id`); `job_items.campaign_id` and `user_id` are both `uuid NOT NULL` and **`campaign_id` carries no foreign key and no check** (M3's test-send sets it to the user's id); `recipient_email`, `rendered_subject`, `rendered_body` are `NOT NULL` (a NULL becomes an opaque 500, not a clean 4xx); `status` must accept `'pending'`; the module roles' grants on these tables are issued **by the module migrations** (M2 `SELECT`/`SELECT`; M3 `SELECT` on users, `INSERT, SELECT` on job_items) and their own tests assert those exact sets, so the platform grants the module roles nothing; no row-level security on either table; plain hard `DELETE` is possible but destructive (module foreign keys cascade) so the platform never grants it.

## Open decisions (yours)

1. **M1's roles `cp_runtime` / `cp_admin` are RENAMED** to `verify_app` / `verify_admin` by 0016 (not replaced by new roles), so every grant they held carries over by construction, and a test proves it; the old names no longer exist. `verify_owner` is new. `verify_app` becomes `LOGIN`; its password is set out of band. If you would rather keep the old role names alive alongside, say so — it is a one-line change in 0016, but nothing deployed uses them.
2. **Scheduled jobs and "one active job per module per user".** Default here: the unique index covers `running`, `paused`, `cancelling` only; a `scheduled` job (credits reserved, not started) does **not** occupy the slot, and P4's start rule checks it. If you want a scheduled job to block a second one, the index changes (a migration, not a rewrite).
3. **Vendor-fallback price seed.** The plan says "admin-set, > 1". Seeded 2 so the table is complete; the CHECK is `> 1`. Pick the real number before launch.
4. **No clawback kind.** The locked kinds are grant / reserve / charge / release / m3_*; a mistaken grant has no kind that reverses it (a negative grant is refused by the sign check). Adding `adjust` is additive (a `CHECK` edit). P2 decides.
5. **`platform.admins` is added** (not in the plan's table list): "a named admin" has to be a row to be a foreign key. Admins are created out of band (migration/runbook), not by the app, until you say otherwise.
7. **Supabase role provisioning (A4) — needs your ruling.** On Supabase the migrator is not a superuser and cannot run module 2's and 3's bootstraps as shipped (eight statements, listed in `tests/supabase/baseline-blockers.txt`). Proposed fix, **no module change**: run `tests/supabase/preprovision.sql` once, as the migrator, before the module chains (it creates `send_managed_owner` and `send_byo_owner` and grants them to the migrator `WITH INHERIT TRUE, SET TRUE`); the FIXED pass proves the whole chain then runs clean. Alternative: change the two bootstraps in M2 and M3 to grant their own owner role to the migrator, as I did for the platform and M1. Say which, and I then move the main harness onto the Supabase image (its migrators would run as `postgres`).
8. **Readiness is now all-or-nothing for M1's queue.** `buildQueue` always declares the queue part of `/readyz`, so a deployment that wants only `/v1/verify` and never sets `TM_QUEUE_ADDR_KEY` is permanently not-ready; there is no "no bulk wanted" setting. That is what the brief asked for (not-ready with that reason); say so if a verify-only mode is wanted.
9. **Retired roles.** 0016 renames `cp_runtime`/`cp_admin`; when a second database in the same cluster re-creates them (migration 0005), 0016 moves that database's grants across and drops the old role if nothing depends on it. Nothing deployed used them.
6. **Supabase Data API.** On a Supabase project, tables a migration creates in `public` are readable by `anon`/`authenticated` through the REST API unless revoked. B2 revokes them explicitly (and the Supabase job asserts it); whether to also enable RLS is yours.

## Findings (flagged, not fixed)

- **F16.** M1's runtime role lacked `INSERT`/`UPDATE` on `policies`, which `EnsurePolicy` needs at startup; no test called `EnsurePolicy`. Fixed in M1 (0016 + a test that runs the real store as `verify_app`) because it blocks "M1 connects as `verify_app`"; recorded here as a module defect that Phase 0's "runs as a superuser" hid (F3).
- **F17.** M1 migration 0014 hard-codes `public` and the role names inside two function bodies; moving the tables alone would have broken every partition-maintenance call and aborted a fresh install. 0016 re-creates both functions.
- **F18.** M3 **writes** a platform table (`job_items`, test-send). Several M3 comments and migration headers still say "read-only" (bootstrap 0000, 0012, the fixture header, two handler comments). Stale module text, not changed.
- **F19.** **M2 requires a system user**: the all-zero uuid row in `public.users` (shared pools and accounts answer 409 without it). That user has no Supabase auth account, so a plain `public.users.id → auth.users.id` foreign key cannot hold it. Design in B2: `auth_user_id uuid UNIQUE REFERENCES auth.users(id)` (nullable) plus `CHECK (auth_user_id = id OR id = '00000000-0000-0000-0000-000000000000')` — the foreign key is real for every real user and the single exception is named in the database. Locked decision "users.id links to auth.users.id" is kept for every user but one.
- **F20.** The modules' pre-flights (`db/preflight/check_platform_tables.sql`, identical in M2 and M3) check **existence only**, by their own comment ("a shape check would break whenever the platform legitimately adds a column"). So "the modules' pre-flight table-shape checks pass" can only mean *their existence checks pass* plus **the platform's own shape check**, which B1/B8 build: the declared module reads are compared with the catalog, and every module statement touching the two tables is `PREPARE`d against the real tables as that module's role. No module is changed.
- **F21.** The modules' fixture (`deploy/pg-init/00-platform-fixtures.sql`, identical in both) makes every column nullable and gives no foreign keys; the code needs several `NOT NULL`s and a primary key plus `REFERENCES` privilege for its foreign keys. The Phase 0 harness used that fixture; it is replaced in B2.
- **F22.** Module foreign keys cascade from `public.users` (M2 7, M3 11; `pools.user_id` / `accounts.user_id` are `RESTRICT`) and from `public.job_items` (`jobs.job_item_id … ON DELETE CASCADE`). Deleting a platform user or job item destroys module history. The platform grants `DELETE` on neither, and a grants test pins that.
- **F23.** M1 has no migration tracker: every migration is `IF NOT EXISTS`, so re-running 0001–0015 on a database that already ran 0016 silently re-creates *empty* tables in `public`. 0016 refuses to proceed if it finds a name in both schemas, and the allowlist gate fails on any such leftover; the README now says so.
- **F24.** On Supabase the migrator `postgres` is not a superuser: `ALTER … OWNER TO verify_owner` and `CREATE SCHEMA … AUTHORIZATION` need membership in the new owner role. 0016 grants the role to the migrator when it is not already a member. Whether M2/M3's and the platform's own bootstrap do the same is exactly what chunk A4 measures.
