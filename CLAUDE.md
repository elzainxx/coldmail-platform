# coldmail-platform — operating rules

The platform is the product users and the admin touch. The three modules do the work (verify = M1, send-managed = M2, send-byo = M3); the platform owns users, money, jobs, authoring and administration, and is the **first real caller of the module contract**.

- The roadmap and the **locked decisions**: [`Docs/coldmail-platform-build-plan.md`](Docs/coldmail-platform-build-plan.md) (diagram: [`Docs/coldmail-platform-architecture.mermaid`](Docs/coldmail-platform-architecture.mermaid)). Locked decisions are **not reopened here**: if one contradicts the module code, **flag it, do not fix it**, and put it in the phase spec's open decisions.
- The spec of the phase being built: `Docs/phase-N-spec.md`. **No code for a phase before its written spec**, and the build plan's status table is kept current from the first commit of the phase.
- The twenty false-green classes: [`deferrals-and-false-greens.md`](deferrals-and-false-greens.md). **Read it before writing a gate.**

## Inherited rules (from building the three modules — verbatim from the build plan)

- **CI on a real GitHub runner is the source of truth.** Local runs are rehearsal. Docker Desktop masked two failures that a Linux runner caught.
- Every test has a **paired control that fails when the property breaks**. A test that cannot fail is not a test.
- Concurrency tests **prove contention** (a forced interleave, or a backend proven blocked), never hope for it.
- **Gates, not comments.** "Remember to do X" becomes a CI check that fails when X is missing.
- Every new test or gate is **proven to run in CI**, not merely to exist; test counts are asserted per package with a nonzero floor.
- Any check that covers only part of its domain **prints how much it did not check**.
- When a behaviour is put behind a switch, sweep every assertion that assumed it was unconditional.
- **The admin surface is a parallel write path.** Every user-path rule is enforced in the store layer, where all writers pass.
- Config, not code. Every dial is seeded with a consumer at the commit that seeds it.
- Base images pinned by digest; CI builds without cache.

## Rules added in Phase 0

1. **A test that cannot run FAILS; it never skips.** The floor gate counts a skipped test as red. Integration tests live behind the build tag `harness` so that `go test ./...` never needs a database and can never skip into a green.
2. **A gate whose subject is empty is red.** Every gate states a nonzero floor on what it found ("found 0 packages/images/migrations — the instrument matched nothing").
3. **Every reject case of a selftest asserts the REASON it fails for**, not only a non-zero exit (class 10). Every selftest has a hard minimum case count and a control that proves the selftest itself can fail.
4. **A gate that reads a log reads the log the step actually produced**, captured with `tee` under `pipefail`, never a summary the step wrote about itself.
5. **The modules are never mocked and never modified.** The harness builds them from the commits in `tools/modules.lock`, unmodified, and runs them as real services. Where a module ships no recipe (M1 has no control-plane Dockerfile), the platform supplies one beside the harness — it does not patch the module. A module defect is **flagged** in the phase spec's findings, not fixed from here.
6. **Nothing the platform can reach is public.** The harness network is `internal: true` and publishes no port; the exposure check reads two independent instruments.
7. **Secrets are minted per run, written mode 600 under the run's temp directory, masked in the log, and never printed or committed.** gitleaks scans the full history of every branch on every push. `.gitleaksignore` is **empty** (a gate fails on any entry): fault proofs are patches applied to a scratch copy by the `fault-proofs` workflow, never commits on a branch, and a fault that needs a token-shaped string is generated by its leg, not stored.
8. **Line endings are LF everywhere** (`.gitattributes`); every script strips `\r` from what it reads.
9. **The platform uses advisory-lock band `7_xxx_xxx_xxx`** and no other (M3 holds `8_`, M2 holds `9_`).
10. **The platform's database identity is `platform_app`** (LOGIN, not a superuser, no DDL). Migrations run as a separate, privileged identity and are never run by the service.

## Rules added in Phase 1

11. **Fault proofs are patches, not branches.** `ci/faults/<phase>/<gate>.patch` + `.expect`, run by the `fault-proofs` workflow on a scratch copy; a leg is red unless the control is green and the fault is red for the named reason. Prove only gates new or changed in the phase, in one or two dispatches. `check-fault-patches` keeps a patch from rotting between dispatches.
12. **Every module has its own schema and nothing of a module lives in `public`.** `public` may hold only `users` and `job_items` (`tests/public-allowlist.txt`, gate `check-public-schema`, run on every chain in the harness). Every SQL statement a module issues names its schema (`verify.`, `send_managed.`, `send_byo.`).
13. **A CHECK that evaluates to NULL passes.** Every constraint over a nullable column says IS NULL / IS NOT NULL or COALESCEs; the tests insert the NULL case.
14. **Money is integers and the ledger is append-only for everyone.** `bigint` credits, no numeric/float/money column (a catalog test); UPDATE/DELETE/TRUNCATE on the ledger, price history, price snapshot and admin audit are refused by privileges AND by triggers; the balance has exactly one writer, the ledger trigger, and `platform.balance_drift` proves it.
15. **The platform fits the module tables as built.** The shape of `public.users` and `public.job_items` is derived from module CODE (`db/module-reads.txt`); every module statement against them is executed as that module's role in the harness. A column no module reads must be nullable or defaulted; the platform grants the module roles nothing and never deletes from either table.
16. **Migrations that create objects run `SET LOCAL ROLE platform_owner`** (the migrator is made able to by `platform_0000`), so ownership needs no ALTER step; the one exception is the public tables, which need CREATE on `public` and are re-owned.

## Rules added in Phase 2

17. **The install runs on the image CI runs.** `harness`, `db-tests` and `supabase` use the digest-pinned `supabase/postgres`; every migrator connects as the non-superuser `postgres` after the required provisioning step `db/install/preprovision.sql` (`Docs/install.md`, gate `check-install-doc`); only the integration tests use the image's superuser `supabase_admin`, and only to prove a refusal bites or to build scratch databases.
18. **One writer per derived fact, and it is the ledger.** `platform.balances`, `platform.reserves` and `platform.m3_entitlements` are written only by triggers on `platform.ledger`; the application roles cannot write them; a recompute (`balance_drift`, `reserve_overdrawn`, a test per table) proves it. The ledger's own `created_at` is the database's (`ledger_stamp_created_at`).
19. **Money writers of one (user, module) serialise on one advisory lock** in the platform band (`internal/money`'s `LockKey`), taken first in every money transaction; the database CHECKs stay as the second wall; concurrency tests force the interleave and prove both backends blocked.
20. **An outcome that does not map cleanly is flagged, never guessed.** The charge table is data (`internal/charge/rules.psv`), mirrored byte for byte in `Docs/phase-2-spec.md` (`check-charge-table`); `unmapped` is never charged and is reported to the caller.
21. **The platform never reports a module-3 state module 3 was not seen to be in.** A convergence needs an observation read back from module 3's suspension route (`GET /v1/admin/users/{id}/suspension`, never the POST's 200 or 422), made at the wanted version and equal to the wanted state, and `platform.m3_sync` refuses anything else (`m3_sync_converged_only_when_observed_at_version`: `converged_version = want_version` needs `observed_version = want_version` AND `observed` = the wanted state).
22. **Money and entitlement operations are idempotent per business key, enforced by the database** (a unique index per job item for charges, one reserve per job, one release per reserve), not only by the idempotency key code derives.
23. **A head is called verified only when the heavy workflows ran green on that exact SHA and the evidence row cites that run** (gate `check-verified-heads`). Every `**done**` / `done —` row of the build plan's status table and every `CLOSED` row of a close-out table must cite its head (`platform@<sha>`, `verify@…`, `send-managed@…`, `send-byo@…`, `module 1/2/3 <sha>`) and its run URL(s); the gate asks the GitHub API that the required workflows (platform: harness, db-tests, supabase plus go, gates, gitleaks, web, platform-check; a module: its main CI workflow plus gitleaks) concluded `success` on that full sha, that every cited run exists, is green (a cited `/attempts/<n>` is judged by that attempt) and is for a cited head, and that the API was reachable (an unreachable API is red, never green). A commit mentioned but not claimed is written without a repo word before its hash. The documents it reads are listed in `tests/verified-heads-docs.txt`; it needs `GH_TOKEN` with read access to Actions on all four repositories.

## Rules added in Phase 3

24. **The repositories are public: source visible for transparency, all rights reserved, nothing real committed** (owner decision 2026-11-17). Every repository carries the same one-paragraph `LICENSE` (`tests/license-canonical.txt` is its one statement), a `NOTICE` that opens with the same sentences and a `README.md` with the notice line, and none says "confidential" (gate `check-license`: platform `gates`, `platform-check` for the three module clones, the parent's `modules-lock` for all five). No tracked file names a Windows home path, a drive-letter path or an IPv4 address outside the documentation, private and special-use classes unless an allowlist entry says why (gate `check-personal-details`, one allowlist per repository in `tests/personal-details/`, a mandatory reason on each entry and a red for an entry that matches nothing). A path is removed from the file in a forward commit (git history cannot be rewritten); a fault proof that needs such a string builds it at run time. The owner's name in prose and the commit authors stay.

## Rules added in the Phase 3 close-out

25. **Push one commit to one ref at a time.** Pushing one commit to several refs at once once failed to start the workflows on `main` (they had to be dispatched by hand); push one ref, wait for its runs to start, then push the next. A documentation-only head has no heavy run of its own: push a `phase-*` tag at it (one ref, alone) to run every workflow on that exact SHA. The only GitHub deletion ever authorised is the one named in `Docs/phase-3-closeout-spec.md` row E1 (scratch branches; never `main`, a tag or anything in `zexSites`).

## How CI runs (all on `ubuntu-latest`; a Windows run is rehearsal)

| Workflow | What it proves |
|---|---|
| `go` | gofmt clean, build, vet (plain and `-tags harness`), unit tests, the per-package floor |
| `web` | `npm ci` from the lockfile, type-check, build, the built CSS contains the Tailwind utilities, tests, the test-count floor |
| `gates` | every gate's selftest, then each gate on the real repository (`check-migrations`, `check-image-pins`, `check-gitleaksignore`, `check-user-lists`, `check-suppression-writers`, `check-job-writers`, `check-install-doc`, `check-charge-table`, `check-gitleaks-config`, `check-fault-patches`, `check-license`, `check-personal-details`, and last `check-verified-heads`, which asks the GitHub API with the job's own read-only token) |
| `db-tests` | the harness's database-only integration tests (grants, roles, ledger, constraints, balance invariant, module shapes, schema locks, migration lifecycle) against a real Postgres, in minutes (`tests/harness/run-db-tests.sh`); the full `harness` runs them too, plus the module-dependent ones |
| `supabase` | every migration, as the non-superuser `postgres` of the pinned `supabase/postgres` image: BASELINE (no provisioning) and FIXED (the proposed role-provisioning step) |
| `fault-proofs` | dispatch-only: one matrix leg per `ci/faults/<phase>/*.expect`; a leg passes only if its gate is green unpatched and red, at the named step with the named message, patched |
| `harness` | the three modules built from their pinned commits and running as real services beside the platform and one real Postgres; the integration tests; the end-to-end probe; the exposure check; the outage check |
| `gitleaks` | the full-history secret scan, with the scanner proven before it is trusted on every run |
| `platform-check` | every JSON file parses, every internal link resolves, every cross-repo citation resolves, every cited commit exists; and the licence and personal-details gates on the three fresh module clones (check 5, with its own controls) |

**When a workflow runs** (the trigger economy; every workflow is on a newer-run-cancels-older `concurrency` group per ref, except the dispatch-only `fault-proofs`, which is never cancelled):
`gitleaks` on every push and pull request, no path filter. `gates` on every push and pull request, no path filter (prose is NOT skipped: the gates read documents on purpose, and `check-personal-details` reads every tracked file, `Docs/history/` included). `platform-check`
on a change to any `*.md` / `*.json`, `tools/`, `LICENSE`, `NOTICE`, the licence and personal-details gates with their canonical text and allowlists, or its own file (it reads documents), plus its weekly schedule. `go` and `web` when what they read changes (`go`: Go files, `go.mod`/`go.sum`, `db/migrations/`, the four
documents its unit tests read, the floor gate and its file; `web`: `web/`, `tests/floors-web.txt`, the floor gate). The heavy workflows `harness`, `db-tests` and `supabase` on dispatch, on a push to `main` or a pull request that
touches `db/`, `internal/`, `cmd/`, `tests/` (except `tests/license-canonical.txt` and `tests/personal-details/`, data of the two public-release gates that no heavy workflow reads), `tools/modules.lock`, `go.mod`/`go.sum`, `Dockerfile*` or what that workflow itself runs (the exact set is in each workflow's header), on a `v*` or `phase-*` tag push, and (`harness`,
`supabase`, `platform-check`) on their weekly schedule: **a documentation-only push starts none of them**, so a documentation-only head has no heavy run of its own (a run proves the head it ran for: to prove a head, push a `phase-*` tag at it, which runs every workflow except `fault-proofs` on that exact SHA because GitHub does not evaluate path filters for a tag push, or dispatch the ones you need).
A pull request from a fork skips the jobs that read `DEPLOY_KEY_COLDMAIL_*` (`harness`, `supabase`, `platform-check`, `fault-proofs`); a skipped job reads as passing, so such a pull request is judged by the other workflows.
Every `uses:` is pinned to a full commit SHA with the tag in a trailing comment; no workflow uses `pull_request_target` or a self-hosted runner.

To run the harness by hand you need Docker, Go, Node, openssl and the three module checkouts at the pinned commits:
`bash tools/fetch-modules.sh --lock tools/modules.lock <dir>` (a module whose `DEPLOY_KEY_COLDMAIL_*` environment variable is set — VERIFY, SEND_MANAGED, SEND_BYO, read-only deploy keys — is cloned over SSH with that key; one whose variable is empty or unset is cloned anonymously over https, which works once the module repositories are public) then `H_MODULES_ROOT=<dir> bash tests/harness/run.sh`.
Docker is currently down on the owner's machine: **only the runner counts.**

## Re-pinning the modules

1. Edit `tools/modules.lock` (three 40-hex commits), push, and let `harness` go green on the runner.
2. In the parent repository (`elzainxx/coldmail`) move the three submodule pointers to the same commits.
3. `bash tools/check-modules-lock.sh <parent-dir>` must say OK. (The parent repository's `modules-lock` workflow runs it on every push, with the submodules checked out anonymously; it could not while the repositories were private, and all five have been public since 2026-11-17.)
